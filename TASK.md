# Задание хакатона: система анализа изменений СПР

> Постановка составлена по [PDF](Система_анализа_изменений_горизонтальная_1.pdf) и [текстовому описанию](02_ОПИСАНИЕ_ЗАДАЧИ.md). Подробные контракты находятся в выданном каталоге `ЗАДАНИЕ`. Этот документ описывает **что требуется сделать и как это проверят**, не выбирая за команду стек и архитектуру.

**Формат:** сервис/прототип за два дня; команда 3–5 человек.

## 1. Контекст и цель

Система принятия решений (СПР) обрабатывает заявку: применяет правила, рассчитывает модели и пороги, подбирает продукты и выдаёт итоговое решение. Перед выпуском новой стратегии один и тот же набор исторических заявок прогоняют через две версии: **BEFORE (MASTER)** — текущую и **AFTER (BETA)** — изменённую. Ответ по одной заявке содержит сотни значений; вручную сравнить тысячи пар нельзя.

Нужен **многопользовательский веб-сервис**, который по готовым ответам показывает последствия изменения стратегии. Аналитик должен примерно за минуту понять:

- сколько заявок имеют различия и у скольких сменилось итоговое решение;
- какие атрибуты изменились чаще всего, для каких продуктов, партнёров и сегментов;
- что сопутствовало смене решения: стоп-фактор, скор, порог, модель или входные данные;
- где данные изменились, но решение осталось прежним;
- какие конкретно заявки и атрибуты стоят за числом в отчёте.

**Граница работы:** модули 1–2 (сбор исторических заявок и их прогон через СПР) уже выполнены. Команда делает **модуль 3 — приведение, сравнение и проверки данных** и **модуль 4 — просмотр результатов в браузере**. Вызывать СПР не нужно.

## 3. Модуль 3: приведение, сравнение и проверки

### 3.1. Конфигурация и исполнение процедур

Пользователь выбирает датасет, процедуры приведения, сравнения и подготовки фактов для отчёта, набор автоматических проверок и их параметры. Конфигурация сохраняется, её можно запустить повторно и заменить отдельный обработчик **без изменения кода приложения**.

Пользовательский код этих этапов выполняется на **Python**. Для каждого скрипта нужны два источника:

1. Код, написанный или изменённый в интерактивной рабочей области приложения, похожей на Jupyter Notebook; его можно сразу применить.
2. Размещённый в системе файл `.py`, выбранный пользователем и соответствующий установленному приложением контракту входов и выходов.

Контракт процедуры должен определять доступные входы, обязательный результат и диагностику: нормализация отдаёт строки плоской таблицы, агрегация — факты для отчёта, проверка — строки `PASS/FAIL`. **Версионирование пользовательского кода в рамках задания не требуется.**

### 3.2. Нормализация и сопоставление

Каждый ответ приводится к плоским строкам вида «один атрибут одной заявки». Нормализованные строки двух срезов объединяются **вертикально**; поле `SOURCE` сохраняет `BEFORE` или `AFTER`. Сопоставление выполняется позже по `APP_ID` и идентичности атрибута. Горизонтальные колонки `BEFORE/AFTER` допустимы как результат сравнения и представление конкретной заявки, но **не являются форматом технического `UNION`**.

Витрина сравнения должна соответствовать [`docs/СХЕМА_ВИТРИНЫ.md`](<../../платформа данные/ЗАДАНИЕ/docs/СХЕМА_ВИТРИНЫ.md>). Ключ строки: **`(APP_ID, PATH, ARRAY_KEY)`**. Обязательные поля: `APP_ID`, `PREFIX`, `CLASS`, `SUFFIX`, `ARRAY_KEY`, `KEY`, `PATH`, `VALUE_BEFORE`, `VALUE_AFTER`, `ADJUSTED_BEFORE`, `ADJUSTED_AFTER`, `DIFF_FLAG`, `CHANGE_TYPE`. Витрина различает четыре случая:

| `CHANGE_TYPE` | Смысл |
|---|---|
| `SAME` | Атрибут есть в обоих срезах, значения равны. |
| `VALUE_CHANGED` | Атрибут есть в обоих срезах, значение изменилось. |
| `ATTRIBUTE_NEW` | Атрибут появился в `AFTER`. |
| `ATTRIBUTE_LOST` | Атрибут исчез в `AFTER`. |

`DIFF_FLAG` рассчитывается по **исходному значению `VALUE`**, а не по бакету `ADJUSTED_VALUE`: изменение `0.42 → 0.58` нельзя потерять лишь потому, что оба значения попали в один интервал. Бакеты нужны для группировки; границы должны быть одинаковыми для обоих срезов.

В настройке разбора нужно исключить технические `appData.request_id` и `appData.createDateTime`: они отличаются у всех заявок. Список исключений должен изменяться пользователем. Справочники `product_catalog` и `tariff_matrix` можно исключить из анализа, если команда объяснит решение.

**Массивы сопоставляются по выбранному для пути режиму, а не автоматически:**

| Путь массива | Режим и ключ |
|---|---|
| `decisionResult.available_offers[]` | По полям `product_id` + `type` (составной ключ). |
| `decisionResult.product_trials[]` | По полю `product_id`. |
| `…product_trials[].rules[]` | По полю `name`. |
| `…product_trials[].scoring.scoreModels[]` | По полю `modelName`. |
| `decisionResult.scoring[]` | По полю `modelName`. |
| `decisionResult.scoring[].value[]` | **По индексу:** порядок значений вектора значим. |
| `ext_data[]` | По полю `body.action`. |
| `product_catalog[]`, `tariff_matrix[]` | Каждый — по полям `mfo_id` + `product_id`. |

Предусмотрены три режима: **по полям** объекта, **по значению** скалярного элемента без значимого порядка и **по индексу** для вектора. Ключи всех вложенных массивов входят в `ARRAY_KEY`; в частности, `modelName` должен отделять одинаковый предиктор в разных моделях. `rules[].hit` принимает `true`, `false` и `null`. Скоры в `ext_data`, `characteristics` и предикторах модели — разные атрибуты; `pd` указывает выбранную целевую модель и не сводится к первому элементу `scoreModels`.

### 3.3. Разрезы, факты и проверки

Построить **слой разрезов: одна строка на заявку**. Обязательные поля по контракту: `APP_ID`, `DECISION_BEFORE`, `DECISION_AFTER`, `DECISION_CHANGED`, `PRODUCTS`, `TOP_OFFER_BEFORE`, `TOP_OFFER_AFTER`, `PARTNER_TYPE`, `ROUTING_METHOD`, `PD_MODEL_BEFORE`, `PD_MODEL_AFTER`, `CUTOFF_BEFORE`, `CUTOFF_AFTER`, `REJECT_REASON_BEFORE`, `REJECT_REASON_AFTER`, `SCORE_OKB_BEFORE`, `SCORE_OKB_AFTER`. Слой нужен для вопросов «у кого изменилось» и для выданных проверок.

После сравнения сгруппировать данные по измерениям будущего отчёта — пути атрибута, значению или бакету, признаку различия, срезу и присоединённым полям заявки — и подготовить факты **`counts` — количество заявок в группе**. Из каждого показателя должна сохраняться связь с `APP_ID`, чтобы открыть соответствующие заявки и атрибуты. Сводная работает над агрегированными фактами, а не загружает пользователю всю витрину.

Реализовать `MartAPI` для пользовательских проверок: `rows(**filters)`, `count(**filters)`, `app_ids(**filters)`, `segments()`, `total_apps()`. Фильтры можно комбинировать: `path`, `path_prefix`, `key`, `array_key`, `diff_flag`, `change_type`, `value_before`, `value_after`, `app_ids`; точные правила и возвращаемые типы — в `checks/README.md`. Выданные пять проверок выполняются как есть. Пользователь может написать свою проверку по тому же контракту `CHECK` и применить её. Все возвращённые строки объединяются в **один отчёт** со столбцами `LABEL`, `SOURCE`, `ARGUMENT`, `CNT`, `TOTAL`, `METRIC`, `APP_IDS`, `RESULT`, `CONFIDENCE`. `SOURCE` у проверки принимает только `BEFORE` или `AFTER`, а список `APP_IDS` ограничен параметром проверки. `APP_IDS` открывают детали, `CONFIDENCE=LOW` показывается менее ярко, чем уверенное срабатывание.

### 3.4. Журнал выполнения

Логировать все алгоритмические этапы и показывать состояние текущего запуска. Из журнала пользователь должен перейти к коду исполнявшегося этапа — интерактивному коду или выбранному `.py` — в его текущей версии. Длительная обработка **не блокирует интерфейс**: пользователь видит прогресс и понимает, что выполняется.

## 4. Модуль 4: отчёт в браузере

**Готовый отчёт открывается после полного формирования данных; показывать частичные результаты не требуется.** Пользователь переходит к нему по ссылке.

- **Отчёт проверок** — одна таблица результатов всех выбранных проверок, сколько бы их ни было. Для каждой строки видны срез, аргумент, числа, метрика, `PASS/FAIL`, уверенность и переход к заявкам.
- **Сводный отчёт** — изменяемая пользователем раскладка строк, колонок и фильтров по атрибутам, значениям/бакетам, типам изменений и разрезам. Он показывает количества и смещения значений; из числа можно перейти к списку заявок, затем к заявке и значению конкретного атрибута до/после.
- **Документ-отчёт** доступен по ссылке и скачивается как HTML. Из скачанного файла должна работать ссылка на сводный отчёт приложения.

Данные для верхнего уровня должны отвечать на вопрос аналитика, а не быть только таблицей сотен тысяч строк. Отдельно следует показывать смены решения и изменения без смены решения. Различие во внешнем скоре нужно выделять, чтобы аналитик мог отделить возможное влияние входных данных от изменений правил стратегии; одного совпадения событий недостаточно для доказательства причины.

## 5. Нефункциональные требования и дополнительные пункты

- **Многопользовательность:** несколько пользователей работают одновременно, каждый со своими конфигурациями и запусками.
- **Отклик:** расчёт может длиться минуты, но интерфейс остаётся доступным; готовая сводная, изменение раскладки, фильтр и переход к заявке должны быть быстрыми на сотнях тысяч строк.
- **Свобода реализации:** стек, хранение, параллелизм, размещение вычислений и компонент сводной выбирает команда; выбор надо обосновать.
- **Явно необязательное расширение:** начать обработку, пока ещё не поступили все ответы прогона. Это не отменяет требования открывать отчёт после полного завершения.
- **Отдельный раздел постановки — альтернативное мнение ИИ:** после расчёта и проверок система обращается к языковой модели за независимым комментарием о подозрительных изменениях в том же отчёте. Команда решает, какие агрегаты, примеры и результаты проверок передать модели вместо полной витрины. В перечне приёмки и шагов демо этот раздел **отдельно не указан**; его приоритет в материалах не уточнён.
- **Плюс сверх основного списка приёмки:** после перезагрузки страницы пользователь видит состояние своего запуска, а не пустой экран.

Ориентиры из PDF:

| Операция | Минимум | Хорошо | Отлично |
|---|---:|---:|---:|
| Приведение и сравнение всего выданного набора | ≤ 5 мин | ≤ 2 мин | ≤ 30 с |
| Первое открытие сводной | ≤ 5 с | ≤ 2 с | ≤ 0,5 с |
| Смена раскладки, фильтр, переход к заявке | ≤ 5 с | ≤ 1 с | ≤ 0,3 с |
| Повторное открытие готового отчёта | ≤ 5 с | ≤ 1 с | мгновенно |

Прогресс и неблокирующий запуск обязательны. Замеры делают на машине команды; абсолютное время между разным оборудованием не сравнивают. Нужно показать, что замеряли, где было узкое место и какое изменение дало ускорение.

## 6. Приёмка и сдача

Работа принимается как **сквозное приложение: датасет → витрина → проверки → браузерный отчёт**. На защите проверят:

1. Полную обработку 2002 пар и совпадение числа заявок с различиями с эталоном организаторов; затем прогон на отложенных заявках.
2. Корректное различение `SAME`, `VALUE_CHANGED`, `ATTRIBUTE_NEW`, `ATTRIBUTE_LOST`.
3. Выбор и замену Python-процедур и проверок через конфигурацию, поддержку интерактивного кода и файла `.py`, настройку параметров без правок ядра приложения.
4. Исполнение пяти выданных проверок и новой проверки, написанной прямо в приложении; объединение результатов в одном отчёте.
5. Изменяемую раскладку сводной поверх `counts` и путь от агрегата к заявке и атрибуту.
6. Журнал с переходом к коду этапа, видимый прогресс и доступность интерфейса во время долгой операции.
7. Отчёт по ссылке, скачиваемый HTML с переходом обратно в приложение, запуск проекта на чистой машине по README.

**Не принимаются:** один консольный скрипт с CSV вместо приложения; разбор, зашитый в ядро под имена и пути только открытого датасета.

Сдача: ссылка на репозиторий с инструкцией запуска и **демо 20 минут на команду плюс вопросы**. Общий сценарий демо: конфигурация и запуск → журнал и код этапа → итоговые числа → сводная → переход к атрибуту → единый отчёт проверок → новая проверка в приложении → скачанный HTML → объяснение архитектуры и замеров.

ИИ-ассистенты, готовые библиотеки и компоненты сводных таблиц разрешены. Команда должна суметь объяснить свои технические и продуктовые решения.
