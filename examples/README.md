Файлы этой папки — тот же пример, что разобран в [[Модуль 3. Приведение и нормализация данных]] и показан в [[Модуль 4. Визуализация отчёта в браузере]], только в машиночитаемом виде. Их можно скормить прототипу разбора, чтобы проверить реализацию на заведомо известном результате.

## Ожидаемый результат

Разбор `01` и `02` должен дать в точности `03` и `04`; их вертикальное объединение — `05`. Сравнение этих данных должно выявить 14 атрибутов, из которых **`DIFF_FLAG = 1` у пяти**; результат такого диагностического сравнения можно сверить с `06`, но это не отдельный этап основной цепочки.

Пример специально содержит четыре ловушки — если реализация их не обрабатывает, результат разойдётся с эталоном:

1. **Порядок элементов в `scoreCardResult` разный** в BEFORE и AFTER. Сравнение по индексу массива даст 6 ложных различий вместо 2 настоящих.
2. **`rejectReasons` — массив без ключей**, и порядок в нём тоже разный. В `ARRAY_KEY` должно попадать само значение элемента, `SUFFIX = reason`, а `KEY` остаётся пустым: у элемента-скаляра нет имени поля в исходном JSON.
3. **`riskSegment` есть только в AFTER**, `DOCS_EXPIRED` — тоже. Это не «изменение значения», а появление атрибута; в результате всё равно `DIFF_FLAG = 1`.
4. **`calculatedAt` отличается всегда** (значение вида `now()`) — техническое поле, в нормализованные таблицы попадать не должно.

Отдельная проверка: у `scoreCardResult[TAKEUP_RATE_IP].value` значение изменилось `0.42 → 0.58`, но бакет остался `(0.3 – 0.6]`. `DIFF_FLAG` должен быть **1** — различие считается по `VALUE`, не по `ADJUSTED_VALUE`.

## Данные для сводного отчёта

`07` / `08` / `09` — это уже агрегированная витрина (результат шага 20), а не разбор одной заявки: демонстрационный прогон на 440 заявках, по которому построен макет отчёта. Схема: `PREFIX`, `CLASS`, `SUFFIX`, `ARRAY_KEY`, `KEY`, `VALUE_ADJUSTED`, `DIFF_FLAG`, `SOURCE`, `CNT`. `KEY` всегда содержит имя листового атрибута; `PREFIX`, `CLASS`, `SUFFIX` и `ARRAY_KEY` хранят только путь до него или идентификатор элемента массива. Например, `company.decisionResult.decision` хранится как `PREFIX = company`, `CLASS = decisionResult`, `KEY = decision`, а `company.limitResult.Limit.limit` — как `PREFIX = company`, `CLASS = limitResult`, `SUFFIX = Limit`, `KEY = limit`. Именно этот набор подаётся в WebDataRocks — см. `Прототип отчёта WebDataRocks.html`.

`09_pivot_report_demo.xlsx` — тот же отчёт в Excel, для тех, кому удобнее «покрутить» его в привычном инструменте:

- лист **«Сводная таблица»** — строки `PREFIX → CLASS → SUFFIX → ARRAY_KEY → KEY → VALUE_ADJUSTED`, колонки `DIFF_FLAG` × срез, значения — количество заявок;
- лист **«Исходные данные»** — те же 59 фактов с автофильтром;
- значения сводной — **формулы `SUMPRODUCT`**, а не константы: подмените данные на втором листе своими, и отчёт пересчитается.

> [!WARNING] Колонку целиком суммировать нельзя
> Одна заявка даёт по строке на каждый атрибут ответа, поэтому сумма по всей колонке (в файле она подписана «справочно») числом заявок не является. Количество заявок в прогоне видно по любому **одиночному** блоку атрибутов — например `decisionResult.decision`: 123 + 229 + 88 = 440.
