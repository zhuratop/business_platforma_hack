# Техническая спецификация для ИИ-агентов разработки

## 0. Иерархия требований и правила работы

1. [TASK.md](TASK.md) — обязательная постановка хакатона; `docs/СХЕМА_ВИТРИНЫ.md`, `docs/ФОРМАТ_ОТВЕТА.md` и `checks/README.md` в соседнем каталоге `ЗАДАНИЕ` — контракты данных. [proj_spec.md](proj_spec.md) добавляет продуктовые метрики, парную статистику и сценарную оценку риска. При конфликте сохранять совместимость с выданными пятью `check_*.py`.
2. Не вписывать имена полей ответа СПР в ядро импорта, оркестрации, хранения или API. Они живут в подключаемом **Python-адаптере данного формата**. Редактор должен позволять заменить этот код без правки ядра. Обязательные имена полей выходной витрины и `MartAPI`, напротив, фиксированы контрактом задания.
3. После каждой задачи агент оставляет работающий вертикальный срез: код, проверку контракта и короткую запись в README о запуске. Не подменять отсутствующие лимит или `PD_default` значением `scoring.pd`.
4. Подробные правила приёмки берутся из `TASK.md`; этот файл описывает **один выбранный способ реализации**, который можно менять только вместе с контрактами и проверками.

## 1. Стек и границы процессов

| Часть | Выбор | Причина |
|---|---|---|
| Веб-интерфейс | React + TypeScript + Vite | Формы загрузки, рабочая область кода, перестраиваемая сводная и drill-down. |
| API | Python 3.11+ и FastAPI | Один язык с пользовательскими процедурами и проверками. |
| Фоновые расчёты | Отдельный Python worker, очередь в SQLite | HTTP отвечает сразу; тяжёлая обработка не живёт в обработчике запроса. |
| Метаданные | SQLite в режиме WAL | Пользователи, датасеты, скрипты, конфигурации, запуски и журнал. |
| Аналитика | Отдельный DuckDB-файл на прогон | Один процесс строит файл; после закрытия writer проверки и API читают его в режиме `read_only`. |
| Статистика | Python, точный биномиальный тест и парный bootstrap | Результаты воспроизводимы с фиксированным seed. |

DuckDB допускает множество процессов чтения в режиме `READ_ONLY`, но одновременная запись разными процессами в один файл требует иной архитектуры; поэтому **рабочий файл прогона пишет один worker, готовый файл неизменяем** ([DuckDB](https://duckdb.org/docs/stable/connect/concurrency.html)). После записи worker закрывает файл, открывает временный файл только для чтения ради проверок и статистики, а после их успеха публикует его для API. SQLite WAL позволяет чтениям не блокировать запись метаданных ([SQLite](https://www.sqlite.org/wal.html)). FastAPI сам рекомендует выносить тяжёлые вычисления из простых фоновых задач запроса ([документация](https://fastapi.tiangolo.com/tutorial/background-tasks/)).

Предлагаемая структура репозитория:

```text
backend/app/{api,core,storage,workers,plugins,domain,stats,advice}/
backend/tests/{unit,integration,fixtures}/
frontend/src/{pages,components,api,types}/
scripts/default_spr/{normalize.py,compare.py,facts.py}/
scripts/checks/             # копии/ссылки на выданные файлы без изменений
runtime/{uploads,runs}/    # игнорировать в репозитории
README.md, TASK.md, proj_spec.md, tech_spec.md
```

`runtime` и исходный каталог `ЗАДАНИЕ` задаются переменными конфигурации. README описывает создание окружения, запуск API, worker и frontend, а также демонстрационный импорт. Нужны две тестовые учётные записи; каждый API-запрос проверяет владельца конфигурации и запуска.

## 2. Поток данных и состояния

```text
ZIP / каталог → проверка структуры → snapshot конфигурации и кода → QUEUED
→ NORMALIZING → COMPARING → FACTS → CHECKS → STATS → REPORTING
→ READY (или FAILED с журналом)
```

- Приём ZIP через браузер с прогрессом; альтернативно выбор уже доступного серверу каталога **только внутри настроенных корней данных**. Архив распаковывать только в выделенный каталог после проверки путей, расширений, размера и количества файлов. `manifest.json`, два среза, заявленное в манифесте количество и одинаковые множества `APP_ID` из имён файлов проверяются **до** запуска расчёта. Сверку с `appData.application_id` делает адаптер данного ответа, а не универсальный загрузчик. Несовпавшие пары показываются пользователю как ошибка импорта, а не пропадают молча. После импорта входы хранятся как неизменяемый snapshot с контрольной суммой; регистрация серверного каталога также делает копию, чтобы изменение исходных файлов не меняло уже созданный прогон.
- Каждая конфигурация сохраняет идентификаторы/параметры всех обработчиков, правила массивов, исключения, бакеты, статистические параметры и пороги решения. Новый запуск получает неизменяемую копию конфигурации и исполняемого кода; в журнале ссылка на эту копию, а редактор отдельно показывает текущий текст.
- Для расчёта создать `runtime/runs/<run_id>/mart.tmp.duckdb`. После заполнения таблиц закрыть writer; проверки и статистика читают временный файл в режиме `read_only`. После их успеха **закрыть все соединения** к временному файлу (важно для переименования на Windows), атомарно переименовать его в `mart.duckdb`, сохранить готовый HTML и только затем поставить `READY`. При ошибке сохранить диагностику и статус `FAILED`, не публиковать частичный отчёт.
- Worker забирает `QUEUED` транзакцией SQLite, записывает `worker_id` и heartbeat. При аварии зависший запуск переводится в `FAILED` с возможностью запустить **новый** `run_id` из сохранённой конфигурации; готовый файл старого запуска не перезаписывается. Одного worker достаточно для двух пользователей: второй расчёт стоит в очереди, UI обоих остаётся доступным.
- Журнал хранит `run_id`, этап, время, обработано/всего, сообщение, traceback при ошибке, идентификатор скрипта и hash исполняемого текста. API не ждёт завершения worker. Повторное применение нормализации/сравнения/фактов создаёт новый полный запуск; повторный запуск **только проверок** на `READY` создаёт отдельный `check_execution_id`, не меняя DuckDB-файл. Пока новая проверка выполняется или завершилась ошибкой, прежняя готовая версия отчёта остаётся доступной; после успеха версия переключается целиком.
- Базовая система не показывает частичные аналитические результаты. Перезагрузка страницы восстанавливает запуск по `run_id` из SQLite.

## 3. Контракты Python-процедур

Это **контракт нашего приложения** для нормализации, сравнения и подготовки фактов; выданный контракт проверки `CHECK` сохраняется без изменений. Все вызовы выполняются worker-процессом; произвольный код пользователя считать доверенным кодом команды, а не безопасно изолированным публичным плагином.

```python
def normalize(response: dict, app_id: str, source: str,
              params: dict) -> Iterable[dict]: ...

def compare(before_rows: list[dict], after_rows: list[dict],
            params: dict) -> Iterable[dict]: ...

def build_facts(mart, raw_pairs: Callable[[], Iterator[tuple[str, dict, dict]]],
                params: dict) -> dict[str, Iterable[dict]]: ...

# Проверки: точный контракт из checks/README.md
CHECK = {"id": str, "label": str, "params": dict, "entrypoint": run}
def run(mart, params: dict) -> list[dict]: ...
```

`normalize` возвращает `APP_ID, SOURCE, PREFIX, CLASS, SUFFIX, ARRAY_KEY, KEY, PATH, VALUE, ADJUSTED_VALUE` на каждый лист и внутренний `VALUE_KIND` для сохранения типа JSON. `compare` возвращает обязательные поля витрины из схемы; внутренние признаки присутствия и типа допускаются для корректного сравнения. `build_facts` возвращает потоки `segments`, `product_trials`, `offers`, `pivot_facts`; `raw_pairs()` каждый вызов даёт **новый** поток пар, чтобы разные выходные генераторы могли читать вход без хранения всех JSON в памяти. Ядро валидирует выходные схемы и пишет их пакетами. Доменный адаптер может также проверить, совпадает ли идентификатор внутри ответа с именем файла.

Строка `pivot_facts` имеет измерения `SOURCE, PREFIX, CLASS, SUFFIX, ARRAY_KEY, KEY, PATH, VALUE_ADJUSTED, DIFF_FLAG, CHANGE_TYPE, product_id, partner_id` (последние два могут быть пусты), `CNT` и **полный** список уникальных `APP_IDS`. Инвариант `CNT = len(APP_IDS)`. Ядро присваивает `fact_id` и разворачивает список в `fact_memberships(fact_id, APP_ID)`; для полной комбинации измерений допускается только одна строка факта. Усечённые `APP_IDS` разрешены лишь в результате `CHECK`, не в факте сводной. Это гарантирует точный переход от агрегата к заявкам.

Учебные `example/03–05` не содержат `PATH`, а `example/06` уже содержит `PATH` и `CHANGE_TYPE`: при сверке нормализации сравнивать **общие колонки**, а затем отдельно проверять производные поля целевого контракта. `example/06_comparison.csv` содержит 14 строк и 6 отличий (4 `VALUE_CHANGED`, 2 `ATTRIBUTE_NEW`). `examples/06_comparison_app1001.csv` — старый диагностический формат без `PATH`/`CHANGE_TYPE`; он тоже содержит 6 отличий, хотя `examples/README.md` утверждает «пять». Ориентир для итоговой схемы — `docs/СХЕМА_ВИТРИНЫ.md` и `example/06_comparison.csv`.

Рабочая область для каждого скрипта: редактор текста, параметры JSON, кнопка «Проверить на учебной паре», stdout/stderr/traceback и результат в виде первых строк. Источник скрипта выбирается из сохранённого текста или размещённого в разрешённом каталоге `.py`. Путь файла и hash показываются перед запуском. Проверка или процедура с неверным контрактом останавливает соответствующий этап с понятной ошибкой. Установить тайм-аут, лимит вывода в журнал и отдельный процесс; **не обещать полноценную изоляцию вредоносного Python-кода**.

### Канонизация и массивы

- `ARRAY_KEY` собирается из ключей всех массивов на пути через `|`; пример для проверки стоп-фактора: `<product_id>|<rule_name>`. `product_id + type` оффера — один составной компонент. Дубли `(APP_ID, SOURCE, PATH, ARRAY_KEY)` запрещены. Недопустимый символ разделителя в компоненте выявлять явно, чтобы выданная проверка, разделяющая `ARRAY_KEY` по `|`, не получила ложное имя правила.
- Конфигурация задаёт режим каждого из девяти массивов из `docs/ФОРМАТ_ОТВЕТА.md`: по полям, по значению или по индексу. Исключения `appData.request_id`, `appData.createDateTime` — в параметрах, а не в ядре. `decisionResult.scoring[].value[]` — по индексу; `available_offers[]` — по `(product_id,type)`.
- Во внешнем контракте `VALUE` — строка: `true/false` в нижнем регистре, JSON `null` как `NULL`, число в устойчивом десятичном виде. При сравнении использовать `VALUE_KIND` и присутствие строки: строка `"NULL"` не равна JSON `null`, а пустая строка не равна отсутствующему атрибуту. `DIFF_FLAG` считать по исходным типизированным значениям, не бакетам. В `MartAPI` возвращать требуемые контрактом строки, а внутренние признаки хранить отдельно.
- На одном `APP_ID` производить полный внешний join нормализованных строк по `(PATH, ARRAY_KEY)`, затем определить `SAME`, `VALUE_CHANGED`, `ATTRIBUTE_NEW`, `ATTRIBUTE_LOST`. Слой разрезов и показателей строится из исходных пар/витрины, а не из визуальной таблицы.

## 4. Хранение и доступ к витрине

**SQLite:** `users`, `datasets`, `scripts`, `configs`, `runs`, `run_events`, `check_executions`, `check_rows`, `stat_results`, `advice_results`. У каждой пользовательской сущности есть `owner_id`; `runs` содержит snapshot конфигурации, путь готового файла, состояние и heartbeat. В `check_rows` хранить `APP_IDS` как JSON с учётом `app_ids_limit`. Если `CNT > len(APP_IDS)`, UI прямо пишет «показаны первые N из CNT»: произвольная пользовательская проверка не обязана уметь восстановить остальные заявки. Полный drill-down из сводной идёт через витрину, а не через укороченный список проверки. После успешного повторного исполнения проверок переключать единую версию строк и HTML-отчёта атомарно.

**DuckDB на прогон:** `normalized_union`, `comparison_mart`, `app_segments`, `product_trials`, `offers`, `pivot_facts`, `fact_memberships`. Первичные ключи логического контракта: `normalized_union(APP_ID,SOURCE,PATH,ARRAY_KEY)`, `comparison_mart(APP_ID,PATH,ARRAY_KEY)`, `app_segments(APP_ID)`, `product_trials(APP_ID,SOURCE,product_id)`, `offers(APP_ID,SOURCE,product_id,type)`, `pivot_facts(fact_id)`, `fact_memberships(fact_id,APP_ID)`. При нарушении уникальности останавливать этап с примером конфликтующей строки. В `product_trials` сохранить `decision`, `partner_id`, `partner_type`, `pd_model`, `target_score`, `target_score_type`, `cutoff_name/value`, `epr`. **`target_score_type` не переименовывать в вероятность дефолта**.

`pivot_facts` хранит `SOURCE`, путь/части пути, `ARRAY_KEY`, значение или бакет, `DIFF_FLAG`, `CHANGE_TYPE`, `product_id`, `partner_id`, другие разрешённые разрезы и `CNT`. Для каждого `fact_id` проверять инвариант `CNT = COUNT(DISTINCT APP_ID)` в `fact_memberships`. Атрибут внутри `product_trials[product_id]` относится к этому продукту; атрибут уровня всей заявки при фильтре продукта относится ко всем участвовавшим продуктам, что нужно обозначить в UI. Pivot API группирует факты по разрешённым пользователю измерениям, а количество в укрупнённой ячейке считает по **объединению связанных `APP_ID`**, не слепым `SUM(CNT)`: одна заявка может войти в несколько исходных фактов. При drill-down тот же запрос возвращает постраничные `APP_ID`. Контрольный пример: две строки разных атрибутов одной заявки, попавшие в одну укрупнённую ячейку, дают `counts=1` и одну заявку в списке. Для быстрого ответа сначала измерить запросы, затем добавить сортировку/индексы и кеш по `(run_id, filters, axes)`; не объявлять скорость достигнутой без профилирования.

`MartAPI` обязан реализовать `rows`, `count`, `app_ids`, `segments`, `total_apps` и сочетания фильтров `path`, `path_prefix`, `key`, `array_key`, `diff_flag`, `change_type`, `value_before`, `value_after`, `app_ids`. Фильтры соединяются через И; `path` и `change_type` принимают также списки. `rows` отдаёт словари с **точными заглавными именами** колонок контракта; `count` возвращает число **строк**, `app_ids` — уникальные отсортированные идентификаторы, `segments` — одну строку на заявку, `total_apps` — число пар. `PRODUCTS` — разделённая `;` строка идентификаторов: этого ожидает выданная проверка `check_ar_drop_by_product.py`. Рабочее правило для многопродуктовой заявки: `PD_MODEL_*`, `CUTOFF_*`, `REJECT_REASON_*` — отсортированные по `product_id` записи `product_id:value`, разделённые `;`; отдельная таблица `product_trials` сохраняет эти значения по каждому продукту. `PARTNER_TYPE` и `ROUTING_METHOD` — отсортированные уникальные значения через `;`. Это допущение проверяется на пяти выданных проверках и может быть заменено в адаптере, если организаторы уточнят точное представление.

## 5. API и интерфейс

| Маршрут | Назначение |
|---|---|
| `POST /api/session`, `DELETE /api/session` | Вход/выход демопользователя, серверная сессия; доступ к данным по `owner_id`. |
| `POST /api/datasets/upload`, `POST /api/datasets/register`, `GET /api/datasets/{id}` | ZIP, доступный серверу каталог и результат валидации. |
| `GET/POST /api/scripts`, `POST /api/scripts/validate` | Текст/файл обработчика, параметры, пробный запуск на учебной паре. |
| `GET/POST /api/configs`, `POST /api/runs`, `GET /api/runs/{id}` | Конфигурации, запуск, состояние и прогресс. |
| `GET /api/runs/{id}/events`, `GET /api/runs/{id}/scripts/{snapshot_id}` | Журнал и конкретный исполнявшийся текст, включая отдельные проверки. |
| `GET /api/runs/{id}/summary`, `GET /api/runs/{id}/stats` | Основные метрики, статистика, доступность данных. |
| `POST /api/runs/{id}/pivot`, `POST /api/runs/{id}/pivot/apps` | Измерения/фильтры → ячейки counts; выбранная ячейка → страницы заявок. |
| `GET /api/runs/{id}/apps/{app_id}` | Атрибуты одной заявки, два значения и тип различия. |
| `POST /api/runs/{id}/checks`, `GET /api/runs/{id}/checks` | Перезапуск набора проверок и единый результат. |
| `GET /api/runs/{id}/report.html`, `POST /api/runs/{id}/advice` | HTML-отчёт и необязательное мнение ИИ. |

Все маршруты возвращают стабильный JSON (`id`, `status`, `data` или `error.code/message/details`), проверяют `owner_id`, используют пагинацию для списков и не передают 290 тысяч строк в браузер. Редактирование нормализации/сравнения/фактов предлагает «применить и пересчитать» с новым `run_id`; новая проверка на готовом прогоне пересчитывает только проверки. `GET /summary` до `READY` отвечает состоянием, а не частичным отчётом. HTML содержит итоговые метрики, проверки и ограничения интерпретации; ссылка обратно строится из настраиваемого `PUBLIC_BASE_URL`, поэтому скачанный файл ведёт в работающее приложение, а не в относительный `file://` путь.

Pivot-запрос принимает только поля из серверного списка измерений, например `rows=["PATH"]`, `columns=["CHANGE_TYPE"]`, `filters={"product_id":["15210"]}`, `measure="unique_apps"`. Ответ содержит ячейки `{dimensions, count, cell_token}`. `cell_token` связывает `run_id`, раскладку и фильтры; `/pivot/apps` принимает его и страницу, возвращает уникальные `APP_ID` и общее количество. `/apps/{app_id}?cell_token=...` подсвечивает именно те атрибуты заявки, которые попали в выбранную ячейку. SQL-идентификаторы берутся из белого списка, значения фильтров передаются параметрами. Для любой ячейки `count` должен совпадать с размером полного списка заявок при постраничном обходе.

Экраны: **Датасеты → Конфигурация/код → Журнал → Обзор → Сводная → Заявка → Проверки/статистика → Решение/экспорт**. В обзорной карточке всегда видны единица, знаменатель и период. Отчёт проверок показывает исходные `RESULT` и `CONFIDENCE`; `LOW` выделяется мягко, не пересчитывается фронтендом. Для `PD_default`, лимитов и денег при отсутствии дополнительных данных показывать «нет данных» и список нужных полей, не ноль. В сводной пользователь меняет поля строк/колонок/фильтров; ни одна ячейка не открывает сырые JSON всех заявок сразу.

## 6. Расчёт метрик и статистики

### Метрики открытого набора

| Идентификатор | Формула и зерно |
|---|---|
| `app_approval_rate` | `Σ 1[decisionResult.decision=APPROVE] / N_pairs`, отдельно BEFORE/AFTER. |
| `decision_transition` | Четыре счётчика `APPROVE/REJECT × APPROVE/REJECT`. |
| `approved_products` | `Σ 1[product_trials.decision=APPROVE]`, отдельно по срезу; также `approved_products / N_pairs`. |
| `product_approval_rate` | Для продукта: одобренные `product_trials` / все его `product_trials` в срезе. Знаменатель и наличие продукта в обеих версиях показывать явно. |
| `offers` | Число `available_offers` по `type`, число уникальных продуктов и смена `rank=1`. Не приравнивать к одобренным продуктам. |
| `target_score` | `product_trials.scoring.pd.value` с `modelName` и типом соответствующей записи `scoreModels`; числовую парную дельту считать только при одинаковой модели/шкале, смену модели показывать отдельно. |

На полном открытом наборе тестовые ориентиры: `N_pairs=2002`, итоговые одобрения `657 → 496`, переходы `APPROVE→REJECT=273` и `REJECT→APPROVE=112`, одобренные `product_trials` `1544 → 1163`, строки офферов `1559 → 1173`. Для этих переходов точное двустороннее биномиальное `p ≈ 1,254 × 10⁻¹⁶`; это контрольное число для реализации теста, а не доказательство причинности или репрезентативности потока. Числа получены чтением JSON, но **не хардкодятся**. Число заявок с любым отличием сверяется с эталоном организаторов. Выданная `check_ar_drop_by_product.py` применяет **итоговое решение заявки** к заявкам, где продукт встречается, а не `product_trials.decision`; обе метрики в UI называются по-разному.

### Обязательная парная статистика

Единица наблюдения — `APP_ID`; она сохраняется при любых фильтрах и пересэмплировании. Для бинарного исхода собрать `b = APPROVE→REJECT`, `c = REJECT→APPROVE`. Точный двусторонний тест Мак-Немара реализовать как `binomtest(b, b+c, p=0.5, alternative="two-sided")` на несовпадающих парах; при `b+c=0` вернуть `p=1` и нулевую дельту. Показать эффект `Δ = (c-b)/N` в процентных пунктах, а не только `p`. Для 95% интервала эффекта пересэмплировать **пары заявок целиком**: `B=5000`, метод percentile, seed `20260827`. Тот же парный bootstrap использовать для среднего числа одобренных продуктов на заявку и доступных непрерывных показателей. [NIST: Мак-Немар](https://itl.nist.gov/div898/software/dataplot/refman1/auxillar/mcnemar.htm), [SciPy: `binomtest`](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.binomtest.html), [SciPy: paired bootstrap](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.bootstrap.html).

Для продуктового бинарного сравнения использовать заявки с этим продуктом **в обоих срезах**; появившиеся/исчезнувшие продуктовые попытки — отдельные показатели. Для нескольких заранее перечисленных продуктов/партнёров `p` корректировать методом Холма **внутри заранее заданного семейства**, хранить сырое и исправленное значение. Подгрупповые тесты служат диагностике; выпуск по ним не разрешается автоматически. Малые группы и отсутствие несовпадающих пар явно обозначать как недостаточную информацию, даже если формальный `p=1`. Для средних парных дельт значимость определять по интервалу относительно нуля, не изобретая отдельное `p`. Парные интервалы, размеры групп, покрытие, `alpha=0.05` по умолчанию и число пересэмплирований входят в результат. [Основание поправки Холма](https://www.ime.usp.br/~abe/lista/pdf4R8xPVzCnX.pdf).

**Интерпретация:** эти 2002 заявки — наблюдаемый исторический набор, для него дельта не случайна. Интервал и `p` экстраполируют на будущий поток только при допущении репрезентативности и независимости заявок; идентификатора клиента для проверки повторяющихся заёмщиков в наборе нет. Это не рандомизированный онлайн A/B-тест. При разном ответе внешнего источника результат помечать как смешение факторов; показывать анализ подгруппы с неизменным входом, но не выдавать его за доказанный причинный эффект. Нельзя считать незначимый `p` доказательством сохранения метрики; для решения использовать заранее заданные пороги и интервалы на **основных** показателях.

### Дополнительная риск/денежная схема

Принимать отдельный CSV/Parquet с ключом `APP_ID, product_id, SOURCE` либо явно размеченный справочник сегментов. Минимальные поля для риск-анализа: `pd_default`, `pd_horizon`, `pd_model_version`, `pd_calibrated`. Для лимитов: `offered_limit`, `currency`. Для денежного сценария: `take_up_probability`, `ead` **или** `drawdown_rate` при известном лимите, `lgd`, `term`, данные маржи/денежных потоков и затрат. Валидировать `0 ≤ probability ≤ 1`, валюту, отсутствие дублей, покрытие одобренных и сопоставимость горизонтов `pd_default` между срезами. Хранить происхождение каждого поля: `observed`, `model_estimate`, `assumption`.

Если риск-данные есть, показывать среднюю `PD_default` среди одобренных и взвешенную по `EAD` величину; если лимиты есть — средний/медианный и суммарный предлагаемый лимит. Изменение состава одобренных — часть эффекта, поэтому отдельно показывать общую популяцию и парные `APP_ID × product_id`. Сценарные ожидаемые потери: `Σ take_up_probability × EAD × pd_default × lgd`; при `EAD = offered_limit × drawdown_rate` явно показывать прокси. Для нескольких взаимоисключающих офферов одной заявки вероятности выдачи должны суммироваться не более чем до 1, иначе будет двойной счёт. Без этих входов значение — `unavailable`, без подстановки `scoring.pd` и без заявления о прибыли. [Basel: PD, LGD и EAD в ожидаемых потерях](https://www.bis.org/committees/bcbs/basel-framework/standard/cre?allChapters=true&chapter=50).

## 7. Движок вывода и ИИ

Конфигурация решения содержит пороги: максимально допустимое падение одобрения заявок/продуктов, рост `PD_default`, снижение лимита и другие ограничения. Порог и его единица вводятся владельцем стратегии; пустой порог не превращается в ноль. Движок возвращает `preferred_strategy ∈ {BEFORE, AFTER, undetermined}`, `status ∈ {hold_current, needs_data, investigate, pilot_candidate}`, перечень пройденных/нарушенных/неизвестных условий и ссылки на метрики. Для показателя, где больше — лучше, сравнивать 95% интервал `Δ=AFTER−BEFORE` с нижним порогом `−allowed_drop`: весь интервал выше порога — условие пройдено, весь ниже — нарушено, пересечение — неопределённость. Для риска, где меньше — лучше, аналогично сравнивать интервал с верхним порогом `allowed_rise`. Сначала проверять целостность данных и обязательные проверки, затем наличие требуемых порогов/метрик, затем интервалы. Явное нарушение ведёт к `hold_current`, пересечение порога или сбой проверки — к `investigate`, отсутствие требуемых данных — к `needs_data`. Только выполнение всех заданных условий делает `AFTER` кандидатом на пилот, не разрешением на безусловный выпуск. При `hold_current` рекомендуемая стратегия — `BEFORE`; при `needs_data` — `undetermined` с рабочим действием «пока оставить BEFORE».

ИИ вызывается только после построения детерминированной сводки. На вход: версия конфигурации, метрики с числителями/знаменателями и интервалами, результаты проверок, статусы доступности, несколько обезличенных примеров и разрешённые ссылки на `APP_ID`. Сырые JSON и отсутствующие поля не отправлять. Ответ валидировать по схеме `{summary, arguments:[{metric_id,claim}], risks, missing_data, next_step}`; утверждение без `metric_id` помечать как неподтверждённое. Нельзя разрешать модели менять числовые поля или вердикты проверок. При ошибке/отсутствии ключа показывать только детерминированный вывод.

Агенты могут вести независимые каталоги параллельно **после A0**; изменения DTO, SQL-схем и API согласовываются до правок потребителей. Каждый этап оставляет исполняемую команду проверки и короткую запись в README. Реальные проверки: `example/` — 12/14/26/14 строк и 6 изменений; основной набор — 2002 пары, 25 ответов с повтором `product_id` у офферов разных типов, `hit=null`, пять выданных `CHECK`; искусственные пары — атрибут пропал, `null→false`, значение изменилось внутри бакета, новая заявка без пары, две строки одного `APP_ID` в одной сводной ячейке. Сверять точные числа из раздела 6 и примеры, не писать тесты, которые лишь повторяют формулу из кода.

Финальный прогон по README фиксирует версию окружения, параметры машины, время полной обработки и четыре задержки отчёта из `TASK.md`; затем команда репетирует 20-минутное демо. Приоритет — обязательный сквозной сценарий хакатона, затем статистика пользователя; финансовый сценарий и ИИ не блокируют базовую приёмку.
