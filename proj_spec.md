# Проектная спецификация: анализ изменений стратегий СПР

## 1. Назначение

Приложение принимает два среза ответов СПР по одним заявкам — `BEFORE_MASTER` и `AFTER_BETA` — и помогает владельцу стратегии решить, что проверить перед выпуском изменения. За одну минуту после расчёта пользователь должен увидеть масштаб изменений, переходы решений, изменения по продуктам и путь от показателя до исходного атрибута. Полная постановка и критерии приёмки — в [TASK.md](TASK.md); технические контракты для реализации — в [tech_spec.md](tech_spec.md).

**Главный принцип:** отчёт отделяет наблюдение, статистический вывод, сценарный финансовый расчёт и совет. Из двух исторических прогонов нельзя автоматически вывести фактическую прибыль или доказать, что каждое изменение вызвано только новой логикой: ответы внешних источников тоже могут отличаться.

## 2. Что действительно есть в выданных данных

Проверен весь `data/RUN-20260827-0001`: 2002 пары, 4004 JSON. Эти числа — ориентир для самопроверки на открытом наборе, не замена эталону организаторов и не константы в коде.

| Наблюдение | BEFORE | AFTER | Как читать |
|---|---:|---:|---|
| Заявок с итогом `APPROVE` | 657 / 2002 (32,82%) | 496 / 2002 (24,78%) | Дельта −161 заявка, −8,04 процентного пункта. |
| Переходы между итогами | 273 `APPROVE → REJECT` | 112 `REJECT → APPROVE` | Основа парного анализа одобрения. |
| Одобренных `product_trials` | 1544 / 4688 | 1163 / 4688 | Число одобренных продуктов, не число заявок. |
| Строк в `available_offers` | 1559 | 1173 | Может отличаться от числа одобренных продуктов из-за типов оффера. |

Во всех 4004 ответах модели `scoreModels` имеют тип `APPROVAL_PROBABILITY`. Поле `product_trials[].scoring.pd` в этом наборе — **выбранный целевой скор**, а не подтверждённая вероятность дефолта. В JSON **нет кредитного лимита, суммы займа, EAD, LGD, дефолтной метки и калиброванной `PD_default`**. Значение `epr` присутствует, но без суммы, срока, выдачи и затрат не даёт прибыль. Поэтому реальную «среднюю величину лимита», риск дефолта и денежный эффект на этом наборе считать нельзя. Интерфейс должен честно показывать «нет данных» и сообщать, какой дополнительный набор нужен для расчёта.

Аудит структуры подтвердил 25 ответов, где офферы имеют одинаковый `product_id`, но разный `type`: составной ключ обязателен. Встречается `rules[].hit = null`, и его нельзя смешивать с `false` или отсутствующим правилом. В открытом наборе продуктовые попытки присутствуют в обоих срезах для каждой пары заявок; для других прогонов это следует проверять, а не предполагать.

## 3. Пользовательский сценарий

1. **Загрузка.** Перетащить ZIP с `manifest.json` и двумя срезами либо выбрать доступный на сервере каталог. Экран до запуска проверяет структуру, количество пар `APP_ID`, отсутствующие/дублирующиеся файлы и показывает предварительный итог импорта.
2. **Настройка.** Выбрать нормализацию, сравнение, подготовку фактов и проверки; источник каждого Python-обработчика — рабочая область в браузере или файл `.py`. Настроить исключаемые пути, режимы массивов, бакеты, параметры проверок и сохранить конфигурацию.
3. **Прогон.** Получить идентификатор запуска и журнал этапов с прогрессом. Из события открыть исполнявшийся код. Другие пользователи и интерфейс продолжают работать. Отчёт становится доступен после завершения всего расчёта.
4. **Обзор.** Увидеть число изменившихся заявок, матрицу переходов, одобрение заявок и продуктов, частые различия, результаты пяти выданных и своих проверок. Ключевые показатели имеют знаменатель, единицу измерения и ссылку на заявки.
5. **Исследование.** Менять раскладку сводной по пути, типу изменения, бакету, продукту, партнёру и другим разрезам. Переходить из ячейки к `APP_ID`, затем к сравнению конкретного атрибута до/после.
6. **Оценка выпуска.** Видеть парную статистику и заранее заданные допустимые пороги изменения метрик. Получить объяснение «какие сигналы за/против», список недостающих данных и, при наличии настроенного ИИ, второе мнение. Скачать HTML-отчёт со ссылкой на интерактивную сводную.

## 4. Функции базовой версии

### Корректное сравнение

Приложение строит вертикальный `UNION` нормализованных строк с `SOURCE`, затем витрину по ключу `(APP_ID, PATH, ARRAY_KEY)` и четыре типа: `SAME`, `VALUE_CHANGED`, `ATTRIBUTE_NEW`, `ATTRIBUTE_LOST`. Различие считается по исходному значению, а бакет используется только для группировки. Технические `appData.request_id` и `appData.createDateTime` исключаются настраиваемой процедурой. Девять массивов сопоставляются по режимам и составным ключам из `docs/ФОРМАТ_ОТВЕТА.md`; вектор `decisionResult.scoring[].value[]` — по индексу. `null`, `false` и отсутствие атрибута не склеиваются.

Витрина сравнения и слой разрезов соответствуют `docs/СХЕМА_ВИТРИНЫ.md`. Пять файлов из `checks/` работают через `MartAPI` без правок. Новая проверка, написанная в приложении, добавляется к единому отчёту. Агрегированные факты `counts` и связь с `APP_ID` питают перестраиваемую сводную. При укрупнении раскладки заявка считается **один раз в ячейке**, даже если у неё изменилось несколько атрибутов; сумма по разным ячейкам не обязана равняться числу заявок. Источники данных и документации находятся в соседнем каталоге `ЗАДАНИЕ`.

### Метрики, которые можно посчитать сейчас

| Метрика | Зерно и определение | Статус |
|---|---|---|
| Одобрение заявок | Доля `decisionResult.decision = APPROVE` среди всех парных заявок. | Обязательно. |
| Переходы решений | Матрица `BEFORE × AFTER`, в том числе 273 потери и 112 новых одобрений в открытом наборе. | Обязательно. |
| Одобрено продуктов | Сумма `product_trials[].decision = APPROVE`; отдельно среднее число одобренных продуктов на заявку. | Обязательно. |
| Одобрение по продукту/партнёру | Доля одобренных продуктовых попыток среди продуктовых попыток с явным знаменателем; отдельно число заявок, где продукт участвовал. | Обязательно. |
| Офферы | Число строк `available_offers`, уникальных продуктов, типы `standard/manual`, смена верхнего оффера. | Обязательно. |
| Целевой скор | Значение `scoring.pd.value` с названием модели и типом `APPROVAL_PROBABILITY`; распределение и изменение только на сопоставимых парах. | Диагностика модели, **не риск дефолта**. |
| Путь до причины | Изменения правил, `pd.modelName`, `cutOff`, внешнего скора и итогового решения по одному `APP_ID`. | Обязательно; причинность не заявляется без контрольных данных. |

Важно: выданная проверка `check_ar_drop_by_product.py` считает **итоговое одобрение заявки среди заявок с данным продуктом**. Её надо исполнять как есть, но не подменять ею новую метрику одобренных `product_trials`.

## 5. Статистический анализ — обязательный слой решения

Это **парное сравнение одних и тех же заявок**, похожее по форме на A/B, но без случайного распределения людей между версиями. Для выданного набора наблюдаемые дельты точны; доверительные интервалы и `p`-значения имеют смысл только как оценка переноса результата на будущий поток при допущении репрезентативности исторических заявок. Отдельно показывать размер выборки, знаменатель, эффект и неопределённость. «Статистически незначимо» не означает «безопасно».

| Показатель | Метод | Что вывести |
|---|---|---|
| Итоговое одобрение, бинарные продуктовые исходы | Точный тест Мак-Немара по несовпадающим парам; для дельты — 95% интервал парным bootstrap. | Дельта в п.п., потери/новые одобрения, `p`, интервал. |
| Число одобренных продуктов на заявку, скор на сопоставимых парах | Парный bootstrap с единицей пересэмплирования `APP_ID`. | Средняя/медианная дельта и 95% интервал, число пригодных пар. |
| Разрезы по продуктам и партнёрам | Те же парные методы, с заранее заданными семействами гипотез и поправкой Холма на множественные проверки. | Исправленные `p`, размер группы; малые группы помечаются как недостаточные. |

Группы определяются **до просмотра результата**. Для сравнения по продукту знаменатель включает пары заявок, где продукт присутствует в обоих срезах; появление/исчезновение продукта показывается отдельно. Если изменились внешние входы или версия целевой модели, это отдельные страты и ограничения интерпретации. Подгруппы служат для поиска причин и не становятся самостоятельным разрешением на выпуск без заранее заданного правила и учёта множественных сравнений. Проверка значимости не заменяет продуктовый порог существенности: допустимое падение approval rate задаёт владелец стратегии, а не код.

Методология: [парный тест Мак-Немара — NIST](https://itl.nist.gov/div898/software/dataplot/refman1/auxillar/mcnemar.htm), [парный bootstrap — SciPy](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.bootstrap.html), [поправка Холма — оригинальная работа](https://www.ime.usp.br/~abe/lista/pdf4R8xPVzCnX.pdf).

## 6. Риск, лимиты и перевод в деньги

Для расширенного анализа приложение принимает **дополнительный файл на уровне `APP_ID × product_id × SOURCE`** либо справочник по продукту/сегменту: калиброванную вероятность дефолта `PD_default` с горизонтом и версией модели, предложенный лимит, ожидаемую фактическую выдачу или коэффициент использования, `LGD`, долю принятия оффера, срок, маржу/ставку и издержки. Поля должны содержать единицы, валюту, период и источник. При неполной загрузке каждая зависящая метрика получает статус «не рассчитывается» или «сценарная оценка».

- **Качество потока:** средняя и взвешенная по экспозиции `PD_default` среди одобренных, доля высокого риска, изменение состава. Сравнение должно учитывать, что состав одобренных заявок изменился.
- **Лимиты:** средний/медианный предложенный лимит среди одобренных, суммарный предложенный лимит и дельта на сопоставимых `APP_ID × product_id`; лимит нельзя принимать за фактическую выдачу.
- **Ожидаемые потери — только сценарий:** `Σ P(выдачи) × EAD × PD_default × LGD`. Если известен только лимит, `EAD` оценивается через явно заданный коэффициент использования, и отчёт помечает допущение. Простой расчёт `Δлимита × PD` не оценивает прибыль и пропускает `LGD`, выдачу и стоимость денег. Базовая формула потерь согласуется с [Basel Framework, CRE35](https://www.bis.org/committees/bcbs/basel-framework/standard/cre?allChapters=true&chapter=50).
- **Экономический эффект:** показывать лишь при наличии достаточных данных о фактической выдаче/принятии, денежных потоках, сроке, риске и затратах. Иначе — диапазон «что будет при заданных допущениях», без подписи «ожидаемая прибыль».

Для финансовых дельт также нужны парные интервалы по `APP_ID`; пользователь видит, насколько результат зависит от допущений по `PD_default`, `LGD`, выдаче и лимиту.

## 7. Рекомендация и ИИ

Решение о выпуске строится сначала **детерминированно**: качество данных → обязательные проверки → эффект и интервал по одобрению → ограничения по риску и лимитам, если эти данные загружены. Пороги допустимого падения потока, роста дефолтного риска и снижения лимитов задаются в конфигурации и сохраняются вместе с запуском. Вывод содержит сравнение `BEFORE` и `AFTER`, статус «оставить текущую / собрать данные / расследовать / кандидат на пилот» и конкретные аргументы. Если ключевой показатель отсутствует, система не выдаёт безусловное «выпускать». Вывод делается только о двух заданных стратегиях, а не о глобально лучшей стратегии.

На открытом наборе `AFTER` даёт на 161 итоговое одобрение меньше, а выигрыш по дефолтному риску и лимитам измерить нечем. Следовательно, **решение о выпуске `AFTER` нужно отложить до проверки бизнес-порогов и получения риск/лимит данных**. Текущий прогон не доказывает, какая стратегия лучше по прибыли или кредитному риску.

**ИИ-совет — второе мнение:** модель получает агрегаты, статистику, результаты проверок и несколько обезличенных примеров с ссылками на `APP_ID`, а не все сырые JSON. Формат ответа: краткий вывод, три главных аргумента с числом/ссылкой, риски и недостающие данные, следующий шаг. Модель не пересчитывает метрики, не подменяет `PASS/FAIL` и не придумывает `PD_default`, лимиты или деньги. При отсутствии подключения к модели базовый отчёт и детерминированные подсказки работают полностью.

## 8. Архитектурный выбор и границы этапов

Для реализации предлагается **Python/FastAPI + отдельный процесс расчёта + SQLite для конфигураций и журнала + один готовый DuckDB-файл на прогон + React/TypeScript для интерфейса**. Пользовательские Python-процедуры запускаются отдельно от HTTP-обработчиков. Запись в DuckDB завершает один процесс; готовый файл открывается приложением только для чтения. Это поддерживает несколько пользователей и быстрые аналитические запросы без конкурентной записи в один файл ([модель доступа DuckDB](https://duckdb.org/docs/stable/connect/concurrency.html), [WAL в SQLite](https://www.sqlite.org/wal.html)). Полные API, схемы таблиц и границы модулей — в `tech_spec.md`.

| Этап | Демонстрируемый результат |
|---|---|
| 1. Основа обязательного сценария | Импорт открытого набора, настраиваемый разбор/сравнение, 2002 пары, точные счётчики и пять проверок. |
| 2. Полное приложение | Редактор и файл `.py`, фоновый прогон, журнал, два пользователя, сводная и переход до атрибута, HTML-отчёт. |
| 3. Аналитика решения | Раздельные метрики заявок/продуктов/офферов, парная статистика, заданные пороги, сигнал дрейфа внешних данных. |
| 4. Расширения | Подключение риск/лимит данных и сценарные деньги, ИИ-совет, ранняя обработка поступающих пар. |

Этапы 1–3 образуют обязательный результат проекта; при дефиците времени сперва завершить сквозной сценарий хакатона из этапов 1–2. Статистика добавлена как требование владельца проекта. Риск и денежные показатели включаются только при наличии дополнительных данных. Раннее формирование отчёта не требуется: он доступен после полного расчёта.

## 9. Приёмка продукта

1. На открытом наборе обработано 2002 пары; итоговые одобрения и одобренные продукты воспроизводят числа из раздела 2; число **любых** различий сверяется с эталоном организаторов. Неизвестные заявки проходят тот же код и конфигурацию.
2. Все пять выданных `CHECK` исполняются без правок; новая проверка из браузерной рабочей области попадает в единый отчёт. Доступны выбор `.py`, журнал и код этапа, сохранённые конфигурации и повторный запуск.
3. Сводная меняет раскладку, использует `counts`, не суммирует повторно одну заявку как несколько заявок и ведёт от ячейки к `APP_ID`, затем к исходному атрибуту.
4. Статистика использует парные исходы, показывает эффект, знаменатель, 95% интервал и `p` там, где он определён. На игрушечных данных с известным ответом тест Мак-Немара и bootstrap дают ожидаемые результаты. Нехватка риск/лимит данных не маскируется числом или советом «выпускать».
5. Два пользователя независимо работают с конфигурациями и отчётами; длительная задача не блокирует UI; HTML скачивается и ведёт обратно в приложение. На машине команды измерены полный прогон и действия отчёта относительно порогов из `TASK.md`; проект поднимается по README.
