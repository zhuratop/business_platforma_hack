# Автоматические проверки — контракт

Автопроверки пишут **пользователи системы** (риск-аналитики и разработчики стратегий). Ваше приложение должно уметь подключить набор проверок, прогнать их по витрине конкретного прогона и показать результат единой таблицей.

В этой папке пять рабочих проверок. Это **пример и одновременно контракт**: ваше приложение должно уметь подключить и исполнить их как есть, а пользователю — дать написать свои по тому же контракту. На защите мы можем подложить свою проверку.

## Контракт проверки

Каждый файл проверки экспортирует объект `CHECK`:

```python
CHECK = {
    "id":    "ar_drop_by_product",     # уникальный идентификатор
    "label": "Approval Rate по продукту упал",   # что видит пользователь
    "params": {"max_drop_rel": 0.10},  # параметры, настраиваемые в UI
    "entrypoint": run,                 # функция проверки
}

def run(mart, params) -> list[dict]:
    ...
```

Функция возвращает список строк. Строки всех проверок объединяются в один результат:

| Поле | Что содержит |
|---|---|
| `LABEL` | Название проверки |
| `SOURCE` | На каком срезе сработала: `BEFORE` или `AFTER`. Проверка, которая сравнивает срезы, пишет `AFTER` — сравнение живёт в слое BETA |
| `ARGUMENT` | Предмет проверки: продукт, скоркарта, атрибут, стоп-фактор |
| `CNT` | Количественный показатель — сколько заявок попало |
| `TOTAL` | База, относительно которой считается `CNT` |
| `METRIC` | Числовая метрика проверки (доля, разница, значение) |
| `APP_IDS` | Идентификаторы заявок, максимум `params["app_ids_limit"]` штук |
| `RESULT` | `PASS` / `FAIL` |
| `CONFIDENCE` | `HIGH` / `LOW` — см. ниже |

### CONFIDENCE и мягкая подсветка

Если срабатываний мало (по умолчанию меньше `params["low_confidence_cnt"]`, обычно 5), проверка ставит `CONFIDENCE = "LOW"`. В отчёте такие строки нужно выделять **бледным** цветом, а не ярко-красным: сигнал есть, но уверенности в нём нет. Это требование к вашему UI, а не к проверке.

## MartAPI — как проверка обращается к витрине

Проверка не знает, где и как вы храните данные. Она получает объект `mart` со следующими методами. **Реализовать этот интерфейс — ваша задача**: поверх SQL, DuckDB, pandas, собственного индекса в памяти — как сочтёте нужным.

```python
mart.rows(**filters)      -> Iterable[dict]   строки витрины сравнения
mart.count(**filters)     -> int              количество строк
mart.app_ids(**filters)   -> list[str]        уникальные APP_ID, отсортированные
mart.segments()           -> Iterable[dict]   слой разрезов, строка на заявку
mart.total_apps()         -> int              всего заявок в прогоне
```

Поддерживаемые фильтры (все необязательны, комбинируются через И):

| Фильтр | Значение |
|---|---|
| `path` | точный `PATH` атрибута, либо список путей |
| `path_prefix` | `PATH` начинается с этой строки |
| `key` | имя атрибута |
| `array_key` | ключ элемента массива |
| `diff_flag` | `0` или `1` |
| `change_type` | `SAME` / `VALUE_CHANGED` / `ATTRIBUTE_NEW` / `ATTRIBUTE_LOST`, либо список |
| `value_before`, `value_after` | точное значение |
| `app_ids` | ограничить набором заявок |

Схемы строк — в [`../docs/СХЕМА_ВИТРИНЫ.md`](../docs/СХЕМА_ВИТРИНЫ.md).

> Требование к производительности: проверки вызывают `mart` многократно и на больших выборках. Нужны индексы.

## Результат — один отчёт

Строки всех проверок объединяются в **единую таблицу**. Схема строки — в [`../docs/СХЕМА_ВИТРИНЫ.md`](../docs/СХЕМА_ВИТРИНЫ.md), раздел «Результат автоматической проверки».

Из строки проверки пользователь должен уметь перейти к заявкам из `APP_IDS` и посмотреть их различия. Это связь между отчётом проверок и разбором в модуле 4.

## Что стоит помнить

- Проверки обращаются к витрине **многократно**. Витрина на выданном датасете — около 290 тысяч строк. Наивная реализация «каждый вызов — полный проход» уложит вас по времени.
- `CONFIDENCE = "LOW"` ставится, когда срабатываний мало. В интерфейсе такие строки стоит подсвечивать бледно, а не ярко-красным.
