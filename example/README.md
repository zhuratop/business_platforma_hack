# Учебный пример: приведение данных по этапам

> [!WARNING] Структура здесь другая, чем в вашем датасете
> Пример намеренно упрощён: в нём **12 строк на заявку, которые читаются глазами**, а не 139. Имена полей — `company`, `scoreCardResult`, `TAKEUP_RATE_IP` — в датасете вы их не найдёте и искать не нужно.
>
> Пример показывает **метод**: как из документа получается плоская таблица и как две таблицы превращаются в сравнение. Формат ваших данных описан в [`../docs/ФОРМАТ_ОТВЕТА.md`](../docs/ФОРМАТ_ОТВЕТА.md), целевая схема — в [`../docs/СХЕМА_ВИТРИНЫ.md`](../docs/СХЕМА_ВИТРИНЫ.md).

Одна заявка, `APP_ID = 1001`, прогнанная через две версии стратегии.

| Файл | Этап | Строк |
|---|---|---|
| `01_response_BEFORE.json` | вход: ответ до изменения | — |
| `02_response_AFTER.json` | вход: ответ после изменения | — |
| `03_normalized_BEFORE.csv` | приведение: плоская таблица по BEFORE | 12 |
| `04_normalized_AFTER.csv` | приведение: плоская таблица по AFTER | 14 |
| `05_union.csv` | склейка двух срезов | 26 |
| `06_comparison.csv` | сравнение с признаком различия | 14 |

CSV: разделитель `;`, UTF-8 с BOM.

---

## Этап 1. Ответ → плоская таблица

На входе — документ. Задача: обойти его до листьев и выдать таблицу, где **одна строка = один атрибут одной заявки**. Дальше вся система работает только с этой таблицей и про JSON уже не знает.

Из ответа BEFORE получилось 12 строк, из AFTER — 14: в AFTER появились два новых атрибута.

Что происходит на этом этапе:

- **Путь до листа становится ключом.** `company → decisionResult → decision` раскладывается в колонки `PREFIX` / `CLASS` / `SUFFIX` / `KEY`.
- **Элементы массивов опознаются по ключу, а не по позиции.** В примере скоркарты `TAKEUP_RATE_IP` и `PD_RETAIL` лежат в массиве, и в двух срезах их порядок разный. В таблице порядок уже не имеет значения: строки идентифицируются по `ARRAY_KEY`.
- **Технические поля отсеиваются.** В ответе есть поле со временем расчёта, оно отличается всегда. В таблицу оно не попало.
- **Значения получают бакеты.** `117325` → `(100K – 250K]`, `0.42` → `(0.3 – 0.6]`. Это колонка `ADJUSTED_VALUE`, нужна для группировки в отчёте.

Обратите внимание: обе таблицы имеют **одинаковую схему**. Именно поэтому их можно просто склеить.

## Этап 2. Склейка

`05_union.csv` — 26 строк: 12 из BEFORE и 14 из AFTER, вертикально, с признаком среза в колонке `SOURCE`. Промежуточный результат, из которого считается сравнение.

## Этап 3. Сравнение

`06_comparison.csv` — 14 строк, по строке на каждый уникальный атрибут заявки. У каждой — значение в BEFORE, значение в AFTER, признак различия и тип изменения.

Из 14 атрибутов изменились 6: четыре сменили значение, два появились в AFTER. Тип изменения стоит в колонке `CHANGE_TYPE`. По этой таблице читается вся причинно-следственная цепочка: решение ушло из `APPROVE` в `VERIFICATION`, потому что появился новый стоп-фактор `DOCS_EXPIRED`; параллельно перекатали скоркарту `TAKEUP_RATE_IP` (`v3 → v4`) и лимит упал из бакета `(100K – 250K]` в `(0 – 100K]`.

### Два места, на которые стоит посмотреть внимательно

**`TAKEUP_RATE_IP.value`: `0.42 → 0.58`, различие есть, а бакет тот же.** Оба значения попадают в `(0.3 – 0.6]`. Различие считается по фактическому значению, не по бакету — иначе изменение потерялось бы.

**Ложных различий по массивам нет,** хотя порядок элементов в двух срезах разный — и в скоркартах, и в списке стоп-факторов. При сравнении по индексу мы получили бы 6 «различий» в скоркартах и 3 в стоп-факторах из воздуха.

## Чего в примере нет

Кода. Ни разбора, ни сравнения — только их результат на каждом этапе. Как приводить данные, вы решаете и реализуете сами; здесь показано, **что должно получиться**.

## `Сводная_таблица_пример.xlsx` — про сводную таблицу

Отдельный файл, и он не про этот учебный пример, а про **сводные таблицы**.

Внутри: лист «Витрина» — результат приведения и сравнения по **100 заявкам из вашего датасета** (структура и имена полей настоящие), и лист «Сводная» — сводная таблица поверх него.

Откройте, встаньте на сводную и перетащите поля между строками, колонками и фильтром. Данные те же — разрез другой. Именно это в задании называется «изменяемая раскладка»: её меняет пользователь, а не разработчик.

Excel здесь — только способ показать идею, а не образец реализации и не формат сдачи. Точно такую же сводную никто не требует: **способ вы предлагаете сами**. Важно найти, как агрегировать данные по совпадающим атрибутам и довести результат до пользователя в браузере, чтобы разрез менял он, а не разработчик.

Кода приведения в файле нет — только его результат. Это 100 заявок из 2002, числа по ним ничего не говорят об остальных и эталоном не являются. Границы бакетов в `ADJUSTED_*` выбраны для примера — свои вы задаёте сами.
