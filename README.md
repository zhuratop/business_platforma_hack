**Задача:** сравнить ответы двух версий системы принятия решений — BEFORE (MASTER) и AFTER (BETA), найти изменения и дать возможность разобрать их до конкретной заявки и атрибута.

**Быстрый запуск через Docker на одном компьютере:** запустите Docker Desktop, откройте PowerShell в папке проекта и выполните:

```powershell
docker compose up --build -d --wait
```

При стандартных настройках приложение откроется по адресу **http://localhost:8000**. Вход: **alice / demo** или **bob / demo**. Полная инструкция с подготовкой данных и остановкой приведена в разделе 7 ниже.

## 1. Описание решения

Когда меняется кредитная стратегия, одного сравнения числа одобрений недостаточно. Нужно понять, какие заявки получили другое решение, какие правила сработали иначе и какие значения поменялись внутри ответа. При этом массивы в JSON могут поменять порядок, а у одной заявки может быть несколько продуктов и офферов.

Наше приложение загружает два среза одного набора заявок, сопоставляет их по APP_ID и разбирает ответы в общую таблицу атрибутов. Затем оно находит различия, выполняет проверки и готовит отчёт. От числа в сводной можно перейти к заявкам, а от заявки — к конкретному изменённому полю.

Что доступно в приложении:

- **Датасеты.** Импорт каталога или ZIP с JSON, XML и CSV. Проверка парности, сохранение копии входов и контрольной суммы. Повторный импорт одинакового набора не создаёт лишнюю строку в списке. Удаление убирает датасет из выбора, сохраняя данные уже созданных прогонов.
- **Конфигурация.** Выбор процедур чтения, нормализации, сравнения и подготовки фактов. Можно настроить ключи массивов, исключения, бакеты значений, статистику и пороги, предусмотренные проверками. Пользовательская проверка доли изменений позволяет задать свой предел — например, 10%, 20%, 30%, 40% или 50%.
- **Python-процедуры.** Полный исходный код в редакторе, загрузка `.py`, копирование стандартной процедуры и пробный запуск. Кнопка «Использовать в конфигурации» сохраняет процедуру и сразу подключает её. Новые проверки из шаблона получают уникальный CHECK.id; при выборе другой версии с таким же ID прежняя версия отключается. Проверки можно удалить в редакторе или конфигурации: они убираются из текущих настроек, а снимки кода и результаты созданных прогонов сохраняются. Для нестандартного XML или CSV можно написать свой читатель без изменения сервера.
- **Журнал.** Этапы обработки, прогресс, ошибки и ссылка на исполнявшийся код. Можно выполнить расчёт до выбранного этапа, посмотреть сохранённые таблицы и продолжить позже. После завершения показано число уникальных заявок с любыми различиями, включая смену решения; заявка с несколькими изменениями учитывается один раз.
- **Сводная таблица.** Раскрываемое дерево всех атрибутов, фильтры BEFORE/AFTER и DIFF_FLAG, количество уникальных заявок и переход к исходным значениям. При выборе всех DIFF_FLAG срезы разделены на колонки 0 и 1; такое же разбиение есть в HTML. Итог считает уникальные заявки отдельно, а не складывает колонки. Сворачивание родителя скрывает всё поддерево.
- **Автопроверки.** Пять проверок из задания и пользовательские проверки в одной таблице. Видны порог, значение метрики, PASS/FAIL и уверенность. Есть фильтры по тексту, срезу, результату, уверенности и числовым диапазонам. Нажатие на название и аргумент проверки открывает её заявки; выбор заявки показывает атрибуты BEFORE/AFTER. Если проверка вернула только первые APP_IDS, список явно отмечен как неполный.
- **HTML-отчёт.** Полное дерево сводной таблицы и все результаты автопроверок с порогами, метриками и APP_ID. Скачивание доступно только на страницах «Сводная таблица» и «Автопроверки». Дерево раскрывается в скачанном файле без сервера; фильтры страницы не переносятся, в отчёт входит весь прогон.
- **Пользователи и параллельные задачи.** Датасеты, код, конфигурации и прогоны разделены между учётными записями. При первом запуске создаются alice и bob. Worker обрабатывает до **10 задач одновременно**; остальные ждут в очереди. Этапы одного прогона выполняются последовательно.

Статистические расчёты доступны через API. Пользовательский результат представлен в журнале, сводной таблице, автопроверках и скачиваемом HTML.

## 4. Данные

Основной источник — открытый набор из задания: `RUN-20260827-0001`, **2002 пары ответов** BEFORE/AFTER.

Дополнительные внешние данные не загружаются. Названия продуктов и компаний берутся из справочников, доступных в исходных материалах. 

Каталог или ZIP должен содержать `manifest.json` и два среза. Например:

```text
dataset/
├── manifest.json
├── BEFORE/
│   └── APP_1.json
└── AFTER/
    └── APP_1.xml
```

```json
{
  "applications": 1,
  "srez": {
    "BEFORE": {"dir": "BEFORE"},
    "AFTER": {"dir": "AFTER"}
  }
}
```

Один файл содержит одну заявку. APP_ID определяется именем файла без расширения. Форматы в паре могут различаться, но наборы APP_ID должны совпадать. Текстовые файлы должны быть в UTF-8. Стандартный CSV использует колонки `path,value,value_kind`; для другого расположения колонок нужен свой читатель. Правила XML, типы значений и примеры приведены в [описании форматов](docs/INPUT_FORMATS.md).

При подготовке данных приложение:

1. Проверяет структуру пакета, число заявок, пары и допустимость путей.
2. Делает копию входных файлов и вычисляет SHA-256. Последующая правка исходного каталога не меняет результаты прогона.
3. Преобразует транспортный формат в объект заявки и разворачивает вложенные поля в строки.
4. Исключает настроенные ветки. Для открытого набора по умолчанию исключены `appData`, `ext_data`, `product_catalog` и `tariff_matrix`: служебные поля, подробные ответы внешних источников и повторяющиеся справочники. В сводной остаются `decisionResult` и `characteristics`. Исходные файлы и APP_ID сохраняются; вернуть ветку можно, убрав её из `normalize.exclude` и создав новый прогон.
5. Применяет правила массивов и бакеты числовых значений. Исходные значения при этом сохраняются.

`scoring.pd` в этом наборе означает **вероятность одобрения**, а не дефолта. Параметры `PD_RETAIL`, `TAKEUP_RATE_IP` и `limitResult` из учебного примера не появляются автоматически в основном наборе. Без подходящих исходных полей вероятность дефолта, лимиты и денежные показатели считаются недоступными.

## 5. Архитектура и подход

Браузер обращается к FastAPI. Сервер сохраняет настройки и ставит задачу в очередь SQLite. Фоновый worker забирает её и запускает отдельный процесс. Каждый прогон получает свой DuckDB-файл, поэтому параллельные задачи не записывают данные в одну аналитическую базу.

React и TypeScript отвечают за интерфейс и его состояние. Python позволяет выполнять серверную обработку и пользовательские процедуры на одном языке. SQLite хранит небольшие служебные записи и очередь без отдельного сервера БД. DuckDB выполняет аналитические запросы над атрибутами, а отдельный worker позволяет продолжать работу с интерфейсом во время расчёта.

Обработка идёт последовательно:

```text
Импорт → Чтение данных → Нормализация → Сравнение
       → Факты и разрезы → Автопроверки → Статистика → HTML-отчёт
```

Общее ядро отвечает за выполнение этапов, хранение и контроль контрактов. Знание структуры СПР находится в заменяемых Python-процедурах. Для каждого запуска сохраняются входы, конфигурация и точный текст кода. Изменение процедуры в редакторе не переписывает уже полученный результат.

| Где хранятся данные | Содержимое |
|---|---|
| `runtime/meta.sqlite` | Пользователи, сессии, конфигурации, код, очередь, журнал, результаты проверок и статистика |
| `runtime/uploads/<dataset_id>/` | Проверенная копия входного пакета |
| `raw_inputs` в DuckDB | Декодированные BEFORE/AFTER, одна строка на пару APP_ID |
| `normalized_union` | Атрибуты обоих срезов с исходными значениями, типами и бакетами |
| `comparison_mart` | Сопоставленные атрибуты, значения до/после, DIFF_FLAG и тип изменения |
| `app_segments`, `product_trials`, `offers` | Отдельные представления заявок, продуктовых попыток и офферов |
| `pivot_facts`, `fact_memberships` | Аналитические факты и связи с полным набором APP_ID |
| `runtime/runs/<run_id>/` | Рабочий DuckDB-файл, снимки завершённых этапов, готовая витрина и версии HTML |

Интерфейс получает данные через HTTP API. Состояние прогона и журнал опрашиваются примерно раз в 1,5 секунды. Узлы сводной загружаются по мере раскрытия, по 50 элементов; сервер считает уникальные APP_ID и возвращает подписанный токен для точного перехода к заявкам. Готовые аналитические файлы открываются для чтения.

**Сравнение атрибутов.** Ответ превращается в строки с APP_ID, источником, путём, ключом массива, типом и значением. Массивы сопоставляются по настроенным ключам: например, оффер — по `product_id + type`. Перестановка элементов не считается изменением, если порядок не является частью смысла данных. Для значимых векторов можно сохранить сравнение по индексу.

Отсутствующее поле, `null`, `false` и пустая строка различаются. Изменение определяется по исходному типу и значению. Поэтому переход 0,42 → 0,58 останется изменением, даже если оба числа попали в один бакет.

**Подсчёт заявок.** В ячейках сводной считается `COUNT(DISTINCT APP_ID)`. Одна заявка с несколькими продуктами не превращается в несколько заявок. Для перехода к деталям сохраняются связи фактов с полным списком APP_ID. Число заявок, продуктовых попыток и строк офферов рассчитывается отдельно.

**Сохранение и продолжение.** Чтение и нормализация фиксируют данные порциями полных пар; размер по умолчанию — 200. Он задаётся через `processing.batch_pairs` в параметрах конфигурации, от 1 до 500. Для набора 2002 пар используется 200: это уменьшает частоту фиксаций по сравнению с малыми порциями; прогресс обновляется после каждой сохранённой порции. Внутренний writer отдельно записывает строки таблиц пакетами до 10 000 строк — это другой параметр. Завершённые этапы сохраняются отдельно. В журнале можно посмотреть их данные, а остановленный или неуспешный прогон продолжить от последнего завершённого этапа. Незавершённый этап выполняется заново с исходным кодом и настройками. Готовый отчёт публикуется только после завершения всего расчёта.

**Автопроверки.** Пять исходных проверок подключены через MartAPI без изменения их кода: падение одобрения по продуктам, появление/исчезновение атрибутов, изменение внешнего скора, исчезновение стоп-факторов и смена целевой модели. Параметры применяются в соответствии с кодом проверки: например, у исходной проверки смены модели процентного допуска нет и любое найденное изменение даёт FAIL. Прочерк в пороге отражает это поведение. Пользовательская проверка доли изменений сравнивает фактическую долю с `max_share`. FAIL означает обнаруженное условие проверки, а не ошибку приложения.

**Статистика в API.** Единица парного анализа — APP_ID. Для смены бинарного решения используется точный тест Мак-Немара, для интервалов — парный bootstrap с фиксированным seed. Для семейств сравнений применяется поправка Холма. Целевые скоры сопоставляются только для одинаковых продуктов, названий и типов моделей. Базовые доли показаны в процентах, абсолютная разница долей и её интервал — в процентных пунктах. Скоры ОКБ и Эквифакс остаются в баллах бюро.

## 6. Эксперименты и результаты

На открытом наборе получены следующие результаты. Это вычисления по данным, а не константы приложения.

| Показатель | BEFORE (MASTER) | AFTER (BETA) |
|---|---:|---:|
| Заявки в парном наборе | 2002 | 2002 |
| Итоговые одобрения заявок | 657 | 496 |
| Одобренные продуктовые попытки | 1544 | 1163 |
| Строки офферов | 1559 | 1173 |

Одобрение потеряли **273 заявки**, получили — **112**. Итоговая доля одобрения уменьшилась примерно с **32,8% до 24,8%**, разница — **−8,04 п.п.** Точный тест Мак-Немара: `p ≈ 1,254 × 10⁻¹⁶`. Статистика описывает различия на этом наборе; она не доказывает причинность или результат на будущем потоке.

В сохранённом приёмочном прогоне изменения найдены у **502 заявок**, из них у **117** итоговое решение не поменялось. Для числа любых изменений организаторы не предоставили отдельного эталона; заданные контрольные числа по одобрениям, переходам, продуктам и офферам совпали. Количество найденных различий зависит от выбранных исключений и процедур обработки.

При разработке проверяли несколько предположений:

| Что проверяли | Результат |
|---|---|
|Сколько одновременно записей лучше всего обрабатывать | получилось около 200 на нашем железе.|
| Не завышает ли сводная число заявок из-за нескольких продуктов | Проверены уникальный подсчёт APP_ID и полный переход к заявкам |
| Дают ли JSON, XML и CSV одинаковые данные | На четырёх реальных парах проверены совпадение декодированных объектов, полный расчёт и HTML |
| Можно ли сделать подробную аналитику по метрикам (стат. значимостью) | На новых данных эта статистика будет плохо реализуема, а генерация новых LLM слишком не надежна |

Замер импорта исторический, выполнен одним повтором без сброса кеша ОС. Он не является гарантией скорости на другой машине. Полный нагрузочный замер для 10 одновременных прогонов пока не проводился. Подробные результаты прежних проверок и условия замеров — в [VERIFICATION.md](docs/VERIFICATION.md) и [данных замера импорта](docs/import-benchmark.json).


## 7. Инструкция по запуску

### Запуск на одном компьютере через Docker

Все компоненты работают **на одном компьютере**. Docker Compose сам запускает сервер, интерфейс и обработчик задач. Команды выполняются **в одном окне PowerShell**.

1. Установите Docker Desktop, выберите Linux containers и дождитесь запуска движка.
2. Откройте одно окно PowerShell.
3. Перейдите в папку проекта и выполните команды ниже. Если проект лежит в другой папке, измените путь в первой строке. Для первой сборки нужен интернет.

Python и Node.js отдельно устанавливать не нужно.

```powershell
Set-Location 'C:\Users\User\Desktop\Проекты\platforma_hack'
docker compose version
docker compose config --quiet
docker compose up --build -d --wait
docker compose ps
```

Команда дождётся готовности сервера. В `docker compose ps` должны появиться работающие `api` и `worker`; для `api` — статус `healthy`. После этого откройте **http://localhost:8000** в браузере на этом же компьютере. Учётные записи при первом запуске: **alice / demo** и **bob / demo**.

Сервер и обработчик задач запускаются автоматически в контейнерах на этом же компьютере. Worker выполняет до 10 задач одновременно; этапы одной задачи идут последовательно.

Worker запускается после успешной проверки `/api/health`. SQLite, загруженные файлы, снимки этапов и отчёты находятся в общем Docker volume `runtime` проекта Compose. Это отдельное окружение: локальная папка `runtime` с Windows-прогонами автоматически в контейнеры не переносится.

**Данные для Docker.** Можно сразу загрузить через браузер ZIP, например [multiformat-4-pairs.zip](examples/multiformat-4-pairs.zip). Для импорта каталога папка `data` репозитория подключается в оба контейнера только для чтения. В поле «Путь к прогону» указывайте путь **внутри контейнера**:

```text
/input/data/RUN-20260827-0001
```

Windows-путь в этом поле для контейнера не подходит. Если полный набор хранится вне репозитория, создайте файл настроек:

```powershell
Copy-Item .env.example .env
```

В `.env` задайте папку, содержащую `RUN-20260827-0001`:

```dotenv
SPR_DATA_DIR="C:/Users/User/Desktop/платформа данные/ЗАДАНИЕ/data"
```

Для Windows используйте прямые слеши. После изменения `.env` примените настройки командой `docker compose up -d`. Уже созданный `.env` повторно копировать не нужно.

Если порт 8000 занят локальным экземпляром приложения, задайте в `.env`:

```dotenv
SPR_PORT=8001
SPR_PUBLIC_BASE_URL=http://localhost:8001
```

Примените настройки командой `docker compose up -d` и откройте **http://localhost:8001** на этом же компьютере.

Полезные команды:

```powershell
# Проверить настройки без запуска
docker compose config --quiet

# Посмотреть журнал сервера и worker
docker compose logs -f api worker

# Остановить контейнеры; данные в volume сохранятся
docker compose down

# Запустить снова с сохранёнными данными
docker compose up -d

# Пересобрать после изменения кода
docker compose up --build -d

# Выполнить короткие серверные тесты внутри образа
docker compose exec api python -m pytest backend/tests/test_core.py backend/tests/test_report.py -q -p no:cacheprovider

# Проверить API и отдельный worker на четырёх реальных парах JSON/XML/CSV
docker compose exec api python -m scripts.docker_smoke
```

Последняя команда загружает небольшой набор, запускает фоновый прогон, проверяет все семь этапов, контроль одобрений, сводную, HTML и изоляцию пользователей. Она создаёт тестовые датасет, конфигурацию и прогон в Docker volume; полный набор из 2002 пар не пересчитывается.

Не добавляйте `-v` к `docker compose down`, если хотите сохранить данные. Не масштабируйте сервис `worker` через `--scale`: числом параллельных задач управляет `SPR_WORKERS` в `.env`, от 1 до 10. `SPR_DEMO_PASSWORD` применяется только при первом создании пользователей в пустом volume.

### Подготовка данных

Для быстрой проверки используйте готовый [multiformat-4-pairs.zip](examples/multiformat-4-pairs.zip). Он содержит четыре реальные пары, преобразованные в JSON, XML и CSV. Архив можно создать повторно:

```powershell
.\.venv\Scripts\python -m scripts.make_multiformat_sample
```

Полный набор можно загрузить ZIP-архивом или зарегистрировать его серверный каталог. Для каталога задайте корень выданных материалов:

```powershell
$env:SPR_DATA_ROOT = 'C:\Users\User\Desktop\платформа данные\ЗАДАНИЕ'
```

В нём ожидается `data\RUN-20260827-0001\manifest.json` и каталоги срезов, указанные в манифесте. Укажите свой путь, если материалы расположены иначе. Если набор из задания находится в `data` самого репозитория, можно использовать `$env:SPR_DATA_ROOT = "$PWD"`.

### Запуск приложения

После установки зависимостей и подготовки данных выполните в том же окне PowerShell:

```powershell
.\scripts\run.ps1 -Workers 10
```

Скрипт сам запускает обработчик задач в фоне и сервер в текущем окне. Откройте **http://127.0.0.1:8000**. Для остановки нажмите **Ctrl+C** в этом же окне. Используйте один выбранный способ запуска: Docker или этот скрипт.

При чистой установке создаются стандартные процедуры и пять исходных проверок. Сохранённые настройки и прогоны находятся в `runtime`.

Дополнительные параметры для запуска без Docker задаются в этом же PowerShell до вызова `run.ps1`:

| Параметр | Значение по умолчанию и назначение |
|---|---|
| `SPR_DATA_ROOT` | Каталог выданных материалов; ограничивает регистрацию серверных каталогов |
| `SPR_RUNTIME` | `runtime` в корне проекта; рабочие данные приложения |
| `SPR_WORKERS` | 10 параллельных задач; допустимо от 1 до 10, также задаётся через `--workers` |
| `SPR_DUCKDB_THREADS` | 2 потока DuckDB на задачу при обработке таблиц |
| `SPR_JOB_TIMEOUT` | 600 секунд на выполнение задачи |
| `PUBLIC_BASE_URL` | `http://127.0.0.1:8000`; адрес ссылок из HTML-отчёта |
| `SPR_DEMO_PASSWORD` | `demo`; используется при первичном создании локальных пользователей |

### Как пройти демонстрацию

1. Войдите. На странице «Датасеты» загрузите небольшой ZIP или импортируйте полный каталог.
2. Откройте «Конфигурация», выберите датасет, стандартные процедуры и нужные проверки.
3. Оставьте «Полный расчёт и HTML-отчёт» и нажмите «Сохранить и запустить». Либо выберите промежуточный этап, чтобы посмотреть его результат отдельно.
4. В журнале проверьте прогресс, сохранённые этапы и код. Если расчёт остановлен на этапе, нажмите «Продолжить прогон». После READY появится число заявок с любыми различиями, включая смену решения.
5. Откройте «Сводная таблица». При всех DIFF_FLAG каждый срез разделён на колонки 0 и 1. Раскройте `decisionResult`, нажмите на количество в нужной колонке и откройте заявку с подсвеченными атрибутами. Если выбрать один DIFF_FLAG, останется по одной колонке на срез.
6. На странице «Автопроверки» попробуйте фильтры и посмотрите пороги. Нажмите на название проверки, чтобы открыть её заявки и сравнить BEFORE/AFTER. При ограничении APP_IDS будет показано, что список неполный.
7. В «Python-процедуры» создайте новую проверку, измените условие или параметры и нажмите «Использовать в конфигурации». Проверка сохранится и будет выбрана. Затем в «Автопроверки» нажмите «Применить набор из конфигурации»: пересчитаются проверки, готовая витрина останется прежней. Удалить проверку можно в редакторе или конфигурации, с подтверждением.
8. Скачайте HTML со страницы сводной или автопроверок. В нём включены весь прогон, разбиение DIFF_FLAG и все строки проверок. Проверьте раскрытие дерева в скачанном файле.


## 8. Ограничения и дальнейшее развитие

- Пользовательский Python выполняется отдельным процессом с тайм-аутом, но без защищённой песочницы. Усилить защиту приложения.
- Текущий пакетный формат — один файл на заявку в каждом срезе, до 1 ГБ и 50 000 файлов заявок. Большой CSV с множеством заявок нужно предварительно разделить или добавить отдельный импорт такого формата.
- Нестандартная структура XML/CSV требует своего читателя. Если меняется смысл полей, понадобится также адаптер нормализации и фактов, в дальнейшем его можно пробовать гененрить с LLM  на основе нескольких примеров.
- Продолжение использует последний полностью сохранённый этап. Незавершённый этап повторяется; восстановления с произвольной строки внутри него нет.
- Одновременные расчёты делят CPU, память и диск. Число worker-процессов нужно подбирать под машину; больше процессов не всегда означает меньшую задержку.
