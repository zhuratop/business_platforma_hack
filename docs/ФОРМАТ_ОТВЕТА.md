# Формат ответа СПР

Один файл — один ответ СПР по одной заявке. Имя файла — идентификатор заявки: `I32554354.json`. Один и тот же файл существует в двух срезах, `BEFORE_MASTER/` и `AFTER_BETA/`.

В ответе **131–178 листьев** (медиана 139) — столько атрибутов даст нормализация на одну заявку. На выданном датасете это витрина примерно на **290 тысяч строк**.

## Скелет ответа

```jsonc
{
  "appData": {
    "application_id": "I32554354",          // ключ заявки
    "request_id": "6f1c2a94-...",           // ТЕХНИЧЕСКОЕ
    "createDateTime": "2024-01-15T10:30:00Z" // ТЕХНИЧЕСКОЕ
  },
  "decisionResult": {
    "decision": "APPROVE",                  // итоговое решение по заявке
    "available_offers": [ ... ],            // что предложили клиенту
    "product_trials": [ ... ],              // прогон по каждому продукту
    "scoring": [ ... ]                      // расчёт моделей
  },
  "characteristics": { "score_okb": 750, "score_equ": 777 },  // готовые внешние скоры
  "ext_data": [ ... ],                      // сырые ответы внешних источников
  "product_catalog": [ ... ],               // справочник продуктов
  "tariff_matrix": [ ... ]                  // справочник тарифов
}
```

## Технические поля — исключать из сравнения

| Поле | Почему |
|---|---|
| `appData.request_id` | Уникален на каждый вызов |
| `appData.createDateTime` | Момент расчёта, отличается всегда |

Эти два поля различаются **у всех заявок датасета**. Если их не исключить, различия найдутся везде и отчёт станет бессмысленным. Список исключений — часть настройки разбора, а не константа в коде: пользователь должен иметь возможность его менять.

## Три этапа скоринга — не путайте их

Скоры встречаются в трёх местах, и это **не дублирование**, а последовательные этапы:

```
1. Готовые скоры извне        ext_data[] → characteristics
                              score_okb = 750
                                    ↓
2. Расчёт моделей             decisionResult.scoring[]
                              features (предикторы) → value (результат)
                              внешний скор может быть предиктором:
                              у модели V2 в features лежит score_okb
                                    ↓
3. Скорбаллы по продуктам     product_trials[].scoring
                              scoreModels[] — готовые значения
                              pd — ЦЕЛЕВОЙ скор для решения
                              cutOff — порог этого продукта
                                    ↓
4. Оффер                      available_offers[]
```

Одно и то же число закономерно встречается на нескольких этапах: `score_okb` = 750 лежит в `ext_data`, в `characteristics` и в `features` модели V2. Это **три независимых атрибута**, каждый со своим признаком различия. Дедуплицировать их нельзя.

Зато отсюда берутся сильные проверки на согласованность этапов: значение уехало на одном этапе, но не на следующем — значит модель считалась не на тех данных.

**`pd` — не дубль `scoreModels[0]`.** Это указание, какая из посчитанных моделей выбрана целевой для решения по продукту. Выбирает её сама стратегия, поэтому смена `pd.modelName` между срезами — крупное событие, а не техническая деталь.

## Массивы: девять штук, три режима сравнения

Это самое важное место задачи. Элементы массива надо сопоставлять **по ключу**, а не по позиции: иначе одна вставка в начало массива даёт лавину ложных различий. Но есть исключение, где всё наоборот.

| Массив | Режим | Ключ элемента |
|---|---|---|
| `decisionResult.available_offers[]` | по полю | `product_id` + `type` (составной!) |
| `decisionResult.product_trials[]` | по полю | `product_id` |
| `…product_trials[].rules[]` | по полю | `name` |
| `…product_trials[].scoring.scoreModels[]` | по полю | `modelName` |
| `decisionResult.scoring[]` | по полю | `modelName` |
| **`decisionResult.scoring[].value[]`** | **по индексу** | порядковый номер |
| `ext_data[]` | по полю | `body.action` |
| `product_catalog[]` | по полю | `mfo_id` + `product_id` |
| `tariff_matrix[]` | по полю | `mfo_id` + `product_id` |

Три режима:

- **по полю** — массив объектов, элемент опознаётся значением одного или нескольких полей;
- **по значению** — массив скаляров, порядок не значим, ключом становится сам элемент;
- **по индексу** — массив-вектор: модель возвращает вектор чисел фиксированной длины, смысл позиций задаёт сама модель. Здесь позиция значима, и ключом служит индекс.

> **Автоматически эти случаи не различаются.** Для парсера `["AGELOW@21", "NOINCOME"]` и `[0.397, 0.518, 0.494]` — одно и то же: массив скаляров. А сравнивать их надо противоположными способами. Поэтому режим задаётся конфигурацией по пути каждого массива — это часть настройки разбора, которую пишет пользователь.

**Составные ключи обязательны.** В `available_offers` у одного продукта бывают две строки с одинаковым `product_id`, различающиеся только `type`: `standard` — обычный оффер, `manual` — добавленный ручной стратегией. Ключ по одному `product_id` их склеит.

## Что означают поля

### `decisionResult`

| Поле | Значение |
|---|---|
| `decision` | Итог по заявке: `APPROVE` / `REJECT`. Равен `APPROVE`, если одобрен хотя бы один продукт |
| `available_offers[].rank` | Позиция продукта в выдаче клиенту |
| `available_offers[].type` | `standard` — обычный оффер, `manual` — добавлен ручной стратегией |

### `product_trials[]` — прогон по одному продукту

| Поле | Значение |
|---|---|
| `product_id`, `product_name` | Продукт |
| `partner_id`, `partner_name`, `partner_type` | Партнёр: `CURRENT` / `NEW_PARTNER` |
| `tariff` | Тариф продукта |
| `routing_method` | Способ маршрутизации: `referal` / `api` |
| `rules[]` | Правила-стоп-факторы: `name`, `description`, `hit` |
| `rules[].hit` | `true` — сработало, `false` — нет, **`null` — не вычислялось** |
| `decision` | Решение по продукту |
| `rejectReason` | Класс причины отказа: `HARDCHECK` (сработало правило) / `CUTOFF` (не прошёл порог) |
| `rejectReasonCode` | Конкретная причина: имя правила либо имя порога |
| `scoring.scoreModels[]` | Значения моделей: `modelName`, `value`, `type` |
| `scoring.pd` | Целевой скор: `modelName` + `value` |
| `cutOff` | Порог: `name` + `value` |
| `epr` | Эффективная ставка |

### `decisionResult.scoring[]` — расчёт моделей

| Поле | Значение |
|---|---|
| `modelName` | Имя модели |
| `features` | Предикторы модели — переменные скоркарты. **Набор предикторов у разных моделей пересекается, но не совпадает** |
| `value` | Результат: вектор чисел. Последний элемент — итоговое значение модели |

### `ext_data[]` — ответы внешних источников

| Поле | Значение |
|---|---|
| `body.action` | Какой источник: `score_okb`, `score_equ` |
| `body.params.data` | Полученное значение |
| `body.params.ok`, `body.params.error` | Признаки успеха |
| `status` | HTTP-статус ответа источника |

### Справочники

`product_catalog[]` и `tariff_matrix[]` — референсные данные, одинаковые во всех ответах. Присутствуют в каждом ответе, но результатом решения не являются. Можно исключить из сравнения — только объясните это решение на защите.

## На что смотреть внимательно

1. **`hit` принимает три значения**, включая `null`. Переход `null → false` — это изменение или нет? Ваше решение, обоснуйте.
2. **Состав `features` меняется между версиями.** Появление или пропажа предиктора — это изменение состава атрибутов, а не значения. Для аналитика это сигнал «модель перекатали», и он должен быть виден отдельно.
3. **Ключ строки должен включать `modelName`.** Иначе предиктор одной модели «протечёт» в другую, а общий предиктор двух моделей склеится в одну строку вместо двух.
4. **Различие по `VALUE`, не по бакету.** Значение может измениться, не выходя из своего бакета: `0.42 → 0.58` — это изменение, хотя оба попадают в `(0.3 – 0.6]`. Бакеты нужны только для группировки в отчёте. Целевая схема витрины — в [`СХЕМА_ВИТРИНЫ.md`](СХЕМА_ВИТРИНЫ.md).
