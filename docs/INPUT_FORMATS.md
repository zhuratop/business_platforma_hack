# Входные данные: JSON, XML, CSV

## Загрузка и конфигурация

Импортируйте каталог или ZIP через «Датасеты». Контракт пакета сохраняется:

```text
manifest.json
BEFORE/APP_1.json
BEFORE/APP_2.xml
AFTER/APP_1.csv
AFTER/APP_2.json
```

```json
{"applications":2,"srez":{"BEFORE":{"dir":"BEFORE"},"AFTER":{"dir":"AFTER"}}}
```

Один файл содержит одну заявку. APP_ID берётся из имени без расширения; формат в BEFORE и AFTER может отличаться. В одном срезе нельзя иметь `APP_1.json` и `APP_1.xml`: это дубликат, а не две заявки. При импорте проверяются парность, число заявок, синтаксис JSON/XML, непустой CSV, безопасные пути и пределы 1 ГиБ / 50 000 файлов заявок. Синтаксис CSV проверяет читатель с выбранным разделителем. Текст — UTF-8, BOM разрешён. Исходные байты копируются и хешируются, исходный каталог после импорта не используется. DTD и сущности XML запрещены.

«Конфигурация запуска» теперь содержит четыре процедуры:

**Чтение данных → Нормализация → Сравнение → Факты и разрезы.**

Читатель переводит транспортный формат в объект заявки. Стандартный читатель находится в `scripts/default_spr/reader.py`; в интерфейсе виден весь код. Старым конфигурациям автоматически добавляется стандартный читатель; уже созданные прогоны и их снимки не меняются.

Чтобы обработать другую структуру XML/CSV:

1. В блоке «Чтение данных» нажмите «Открыть код».
2. Создайте «Копию в редактор» или загрузите `.py` при выбранном типе `reader`.
3. Реализуйте функцию ниже, сохраните и нажмите «Проверить на паре». Для читателя берётся первая пара выбранного датасета, а не фиксированный учебный JSON. Показаны оба результата и ошибки с именем файла.
4. Выберите новую процедуру в конфигурации и создайте новый прогон.

```python
def read_input(raw: bytes, filename: str, app_id: str, source: str, params: dict) -> dict:
    # filename — относительный путь, source — BEFORE либо AFTER.
    # Вернуть один JSON-совместимый объект; без NaN/Infinity/кастомных объектов.
    ...
```

Читатель может обрабатывать все три расширения или конкретный формат данного пакета. Если структура объекта отличается от СПР, необходимо также выбрать соответствующие нормализатор и адаптер фактов. Транспортный читатель сам не придумывает отсутствующие бизнес-поля.

Сохраняются снимки кода читателя, остальных процедур и параметров. Читатель вызывается один раз для каждого файла в полном прогоне. Последующие этапы используют сохранённые декодированные объекты. Python предназначен для доверенного кода команды, как и остальные процедуры.

## Стандартный JSON

Корень — объект. Типы сохраняются: `null`, `false`, `""` и отсутствующее поле различаются. Массивы сопоставляются последующим нормализатором по настроенным ключам, а не по порядку транспортных строк/элементов.

## Стандартный CSV

Длинная форма с точным заголовком `path,value,value_kind`. Это позволяет передать вложенные структуры без потери типов:

```csv
path,value,value_kind
/appData/application_id,APP_1,string
/decisionResult/decision,APPROVE,string
/characteristics/score_okb,720,number
/extra/flag,false,boolean
/extra/empty,,string
/extra/nullable,,null
/decisionResult/available_offers/0/product_id,5123,string
/decisionResult/available_offers/0/type,MAIN,string
```

Пути — JSON Pointer: `/` в имени ключа экранируется как `~1`, `~` как `~0`. Индексы массива идут подряд с нуля. Числовые сегменты внутри пути трактуются как индексы; объект с числовыми ключами можно передать целиком типом `object`. Допустимые типы: `string`, `number`, `boolean`, `null`, `object`, `array`; контейнер целиком передаётся JSON в ячейке с обычным CSV-экранированием. Пустые контейнеры — `{},object` и `[],array`. Отсутствующее поле не передаётся строкой. Дубликаты пути, разрывы индексов и конфликт значения с дочерними полями отклоняются.

Строки не преобразуются в числа автоматически: `001` остаётся строкой. Разделитель настраивается через `params.reader.csv_delimiter`, например `";"`. Для обычного широкого CSV с собственными колонками загрузите читатель с нужным отображением колонок. Файл с множеством заявок нужно предварительно разделить на файлы по APP_ID: текущий пакетный контракт — один файл на заявку.

## Стандартный XML

Корневой элемент — транспортная оболочка, по умолчанию снимается:

```xml
<response type="object">
  <appData><application_id>APP_1</application_id></appData>
  <decisionResult>
    <decision>APPROVE</decision>
    <available_offers type="array">
      <item><product_id>5123</product_id><type>MAIN</type></item>
    </available_offers>
  </decisionResult>
  <extra>
    <flag type="boolean">false</flag>
    <empty type="string" />
    <nullable type="null" />
    <number type="number">0.42</number>
  </extra>
</response>
```

Без типа лист остаётся строкой, включая пустой элемент. Поддерживаются `type="number|boolean|null|string|array|object"`, `xsi:nil="true"`. Повторяющиеся одноимённые дочерние элементы образуют массив; для массива из одного/нуля элементов используйте явную оболочку `type="array"`. Смешанный текст и элементы, произвольные XML-атрибуты требуют собственного читателя: стандартный не отбрасывает их молча.

Если XML нельзя менять, задайте параметры, например:

```json
{
  "reader": {
    "xml_types": {"characteristics.score_okb":"number", "items[].enabled":"boolean"},
    "xml_arrays": ["items"],
    "xml_keep_root": false
  },
  "processing": {"batch_pairs":25}
}
```

`xml_arrays` обозначает контейнер, дочерние элементы которого — элементы массива. Пути типов внутри него используют `[]`. `xml_keep_root:true` сохраняет корневой ключ (например, `company`); пути типов в этом случае также включают корневой ключ.

## Постепенное сохранение

По умолчанию каждые **25 полных пар** выполняется одна транзакция DuckDB: декодированные BEFORE/AFTER (`raw_inputs`) и нормализованные атрибуты (`normalized_union`). Затем выполняется CHECKPOINT, и только после него обновляются постоянные счётчики `saved_pairs`, `normalized_rows`, `saved_at` и журнал. Размер порции — `params.processing.batch_pairs`, целое от 1 до 500; значение 1 фиксирует каждую пару отдельно.

В журнале интерфейса показано число сохранённых пар и атрибутов, независимо от текущего этапа. При ошибке неполная порция откатывается; предыдущие остаются в `runtime/runs/<run_id>/mart.tmp.duckdb`. Частичный файл не публикуется как готовый отчёт. Чтение этого файла для диагностики возможно после остановки writer. Сравнение и последующие таблицы также записываются порциями штатным writer; новый механизм атомарных полных пар относится к чтению и нормализации.

Автоматического продолжения с последней порции пока нет: после сбоя создайте новый прогон. READY по-прежнему публикуется атомарно после проверок, статистики и HTML; готовые витрины не изменяются.
