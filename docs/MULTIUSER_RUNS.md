# Несколько пользователей, параллельные задачи и сохранение этапов

## Запуск в локальной сети

Из корня проекта, после установки зависимостей и сборки frontend:

```powershell
.\scripts\run.ps1 -Lan -Workers 2 -Port 8000
```

API слушает `0.0.0.0:8000`; интерфейс открывается с других устройств по `http://<IPv4 компьютера-сервера>:8000`. Адрес Wi-Fi/Ethernet можно посмотреть командой `ipconfig`. Адреса VPN и `127.0.0.1` для других компьютеров не подходят. Ссылка в скачанном через API HTML использует адрес, по которому открыт сервис. Для заранее сохранённых worker-отчётов адрес можно задать через `-PublicBaseUrl 'http://<IPv4>:8000'`.

Если входящие подключения блокирует Windows Firewall, администратор может разрешить порт только для частной локальной сети:

```powershell
New-NetFirewallRule -DisplayName 'SPR local service' -Direction Inbound -Action Allow -Protocol TCP -LocalPort 8000 -Profile Private -RemoteAddress LocalSubnet
```

Правило не создаётся приложением автоматически. Гостевая Wi-Fi сеть может запрещать соединения между устройствами.

Ручной запуск в двух терминалах:

```powershell
.\.venv\Scripts\python -m backend.app.workers.main --workers 2
.\.venv\Scripts\python -m uvicorn backend.app.api:app --host 0.0.0.0 --port 8000
```

Это две отдельные команды в разных терминалах. Без `-Lan` скрипт оставляет доступ только с компьютера-сервера.

## Пользователи

Существующие аккаунты: `alice / demo`, `bob / demo`. Каждый пользователь видит только собственные датасеты, процедуры, конфигурации, прогоны, журнал и контрольные сохранения. Для проверки двух пользователей на одном компьютере используйте разные профили или обычное и приватное окно: вкладки одного профиля разделяют cookie.

Создание дополнительного аккаунта на сервере:

```powershell
.\.venv\Scripts\python -m scripts.create_user analyst
```

Пароль запрашивается без отображения и без передачи в аргументах командной строки. Минимум 8 символов. Используйте тот же `SPR_RUNTIME`, что у сервера.

## Выполнить часть расчёта

В «Конфигурации запуска» выберите «Выполнить до этапа»:

| Этап | Сохранённый результат |
| --- | --- |
| Чтение данных | Полные пары объектов после выбранного reader, `raw_inputs` |
| Нормализация | Таблица атрибутов BEFORE/AFTER, `normalized_union` |
| Сравнение | Исходные значения, типы и признаки изменений, `comparison_mart` |
| Факты и разрезы | Заявки, продуктовые попытки, офферы и факты сводной |
| Автопроверки | Результаты выбранных CHECK |
| Статистика | Парные оценки и сводные метрики |
| Полный расчёт и HTML-отчёт | READY, интерактивная сводная и скачивание отчёта |

Этапы имеют зависимости и выполняются по порядку. Например, нельзя сравнить данные до нормализации. Остановка после чтения не запускает нормализацию, сравнение или проверки.

В журнале статус `PAUSED` означает успешное завершение выбранной части, а не ошибку. Доступны список сохранений и просмотр первых 10 строк таблицы последнего завершённого этапа. После проверок и статистики их результаты также можно выбрать в просмотре (`checks`, `stats`).

Для продолжения выберите следующий конечный этап и нажмите «Продолжить прогон». Используется тот же `run_id`, исходный снимок кода и настроек. Завершённые этапы не выполняются повторно. Изменения конфигурации влияют на новые прогоны; для перерасчёта завершённого этапа создайте новый запуск.

## Надёжность и параллельное выполнение

- Один supervisor держит от 1 до 8 рабочих слотов, по умолчанию 2 (`--workers` или `SPR_WORKERS`). Задачи разных пользователей и одного пользователя могут выполняться одновременно; лишние остаются в очереди.
- Каждая задача работает отдельным процессом и пишет отдельный DuckDB-файл своего прогона. На один файл приходится только один writer. Проверки одного READY-прогона сериализуются при выдаче из очереди.
- Чтение и нормализация фиксируют порции полных пар (`processing.batch_pairs`, по умолчанию 25). Незавершённая порция откатывается.
- После закрытия каждого этапа данных публикуется отдельный неизменяемый файл, затем обновляется запись сохранения в SQLite. Проверки/статистика сохраняют результаты в метаданных, используя неизменяемую витрину фактов.
- При ошибке предыдущие завершённые этапы сохраняются. После восстановления worker можно продолжить FAILED-прогон: незавершённый этап повторяется с начала, уже завершённые пропускаются. Это продолжение по этапам, а не с произвольной строки внутри сбойного этапа.
- Перезапуск supervisor сохраняет `PAUSED` и очереди, прерванные активные задачи помечает FAILED с возможностью продолжить. На Windows дерево каждого задания ограничено Job Object: остановка supervisor не оставляет пишущие дочерние процессы.
- Количество потоков DuckDB на задачу задаёт `SPR_DUCKDB_THREADS` (по умолчанию 2). Тайм-аут одной попытки — `SPR_JOB_TIMEOUT`, по умолчанию 600 секунд.
- Сохранения требуют дополнительного места на диске: этапы чтения, нормализации, сравнения и фактов имеют отдельные копии DuckDB. Не удаляйте runtime во время работы сервиса.

## Короткая проверка

```powershell
.\.venv\Scripts\python -m pytest backend/tests/test_pipeline_resume.py -q
```

Проверяются отдельные процессы двух пользователей, изоляция объектов, сохранение/продолжение, неизменность завершённых этапов после ошибки, исходные снимки конфигурации, защита от двух одновременных продолжений и создание аккаунта. Используются только четыре реальные пары из тестовых fixtures.

Браузерная проверка — `frontend/tests/run-stages.spec.ts`: требует работающие API и worker, маленький ZIP `runtime/qa-stages-small.zip`. Для отдельного тестового сервера установите `SPR_TEST_BASE_URL`, например `http://127.0.0.1:8011`, и отдельный `SPR_RUNTIME` у обоих процессов.
