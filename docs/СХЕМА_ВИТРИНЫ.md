# Схема витрины — целевой формат

Это **контракт**. Приведение данных вы пишете сами, но результат должен иметь схему, описанную здесь: по ней работают выданные автоматические проверки, по ней же мы сверяем ваш результат с эталоном.

Три таблицы: витрина сравнения, слой разрезов и результат проверок.

---

## 1. Витрина сравнения — главная таблица

Одна строка = **один атрибут одной заявки**, сопоставленный между срезами.

| Поле | Тип | Что содержит |
|---|---|---|
| `APP_ID` | строка | Идентификатор заявки, он же имя файла |
| `PREFIX` | строка | Первый сегмент пути атрибута |
| `CLASS` | строка | Второй сегмент пути |
| `SUFFIX` | строка | Остаток пути до имени атрибута, через точку. Может быть пустым |
| `ARRAY_KEY` | строка | Ключи всех массивов на пути, через `\|`. Пусто, если массивов на пути нет |
| `KEY` | строка | Имя атрибута — последний сегмент пути |
| `PATH` | строка | Полный путь атрибута **без индексов массивов** |
| `VALUE_BEFORE` | строка | Значение в срезе BEFORE. Пусто, если атрибута в срезе не было |
| `VALUE_AFTER` | строка | Значение в срезе AFTER. Пусто, если атрибута в срезе не было |
| `ADJUSTED_BEFORE` | строка | Значение BEFORE после бакетизации |
| `ADJUSTED_AFTER` | строка | Значение AFTER после бакетизации |
| `DIFF_FLAG` | 0 / 1 | 1 — атрибут изменился, 0 — нет |
| `CHANGE_TYPE` | строка | `SAME` / `VALUE_CHANGED` / `ATTRIBUTE_NEW` / `ATTRIBUTE_LOST` |

### Ключ строки

Пара **(`PATH`, `ARRAY_KEY`)** уникально определяет атрибут внутри заявки. Вместе с `APP_ID` это первичный ключ витрины. Если у вас получаются дубли по этому ключу — значит ключ массива выбран неверно.

### Как считается `DIFF_FLAG`

По `VALUE`, **не по `ADJUSTED_VALUE`**. Значение может измениться, не выходя из своего бакета: `0.42 → 0.58` при бакете `(0.3 – 0.6]` — это изменение, и терять его нельзя. Бакеты нужны только для группировки в отчёте.

### `CHANGE_TYPE`

| Значение | Когда |
|---|---|
| `SAME` | атрибут есть в обоих срезах, значения совпадают |
| `VALUE_CHANGED` | атрибут есть в обоих срезах, значения разные |
| `ATTRIBUTE_NEW` | атрибута нет в BEFORE, есть в AFTER |
| `ATTRIBUTE_LOST` | атрибут есть в BEFORE, нет в AFTER |

Различать эти четыре случая обязательно. «Правило перестало срабатывать» и «правило убрали из стратегии» — разные события, и в отчёте они должны читаться по-разному.

### `ADJUSTED_VALUE` — бакетизация

Приведение значения к интервалу или категории, чтобы группировать близкие значения в отчёте: `117325` → `(100K – 250K]`, `0.42` → `(0.3 – 0.6]`. Для строковых значений обычно совпадает с `VALUE`.

Границы бакетов задаёте вы — это часть пользовательской процедуры. Требование одно: одинаковые для обоих срезов, иначе сравнение поедет.

## 2. Слой разрезов — одна строка на заявку

Витрина отвечает «что изменилось». Разрезы отвечают «у кого». Аналитик по ним фильтрует отчёт: «покажи только по продукту X», «только там, где сменилась целевая модель».

| Поле | Что содержит |
|---|---|
| `APP_ID` | Идентификатор заявки |
| `DECISION_BEFORE`, `DECISION_AFTER` | Решение по заявке в каждом срезе |
| `DECISION_CHANGED` | 0 / 1 — сменилось ли решение |
| `PRODUCTS` | Продукты, участвовавшие в заявке |
| `TOP_OFFER_BEFORE`, `TOP_OFFER_AFTER` | Продукт на первой позиции в выдаче |
| `PARTNER_TYPE` | Тип партнёра |
| `ROUTING_METHOD` | Способ маршрутизации |
| `PD_MODEL_BEFORE`, `PD_MODEL_AFTER` | Целевая модель, по которой принято решение |
| `CUTOFF_BEFORE`, `CUTOFF_AFTER` | Имя применённого порога |
| `REJECT_REASON_BEFORE`, `REJECT_REASON_AFTER` | Класс причины отказа |
| `SCORE_OKB_BEFORE`, `SCORE_OKB_AFTER` | Скор внешнего источника |

Откуда что брать — в `ФОРМАТ_ОТВЕТА.md`. Набор полей можно расширять, но перечисленные должны быть: на них опираются выданные проверки.

## 3. Результат автоматической проверки

Каждая проверка возвращает список строк. Строки всех проверок объединяются в **один отчёт** — единую таблицу.

| Поле | Что содержит |
|---|---|
| `LABEL` | Название проверки — что проверяли |
| `SOURCE` | На каком срезе сработало: `BEFORE` или `AFTER`. Третьего значения нет: проверка, которая сравнивает срезы, пишет `AFTER` — сравнение живёт в слое BETA |
| `ARGUMENT` | Предмет проверки: продукт, скоркарта, атрибут, стоп-фактор |
| `CNT` | Сколько заявок попало |
| `TOTAL` | База, относительно которой считается `CNT` |
| `METRIC` | Числовая метрика: доля, разница, значение |
| `APP_IDS` | Идентификаторы заявок — по ним пользователь переходит к деталям |
| `RESULT` | `PASS` / `FAIL` |
| `CONFIDENCE` | `HIGH` / `LOW` |

`APP_IDS` — это связь между отчётом проверок и разбором различий: из строки проверки пользователь должен попадать к этим заявкам.

`CONFIDENCE = LOW` означает, что срабатываний мало и уверенности в проблеме нет. Такие строки стоит подсвечивать бледно, а не ярко-красным: аналитику важно отличать «сломали» от «шум».

## Как проверки обращаются к витрине

Проверка не знает, как вы храните данные. Она получает объект доступа с пятью методами:

```python
mart.rows(**filters)      -> строки витрины сравнения
mart.count(**filters)     -> количество строк
mart.app_ids(**filters)   -> уникальные APP_ID, отсортированные
mart.segments()           -> строки слоя разрезов
mart.total_apps()         -> всего заявок в прогоне
```

Реализовать этот интерфейс — ваша задача: поверх SQL, аналитической БД, датафрейма, собственного индекса в памяти. Полный список фильтров — в `../checks/README.md`.

> Проверки обращаются к витрине многократно и на больших выборках. Витрина на выданном датасете — около **290 тысяч строк**. Реализация «каждый вызов — полный проход» уложит вас по времени: нужны индексы.
